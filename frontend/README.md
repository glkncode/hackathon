# AI Document Assistant — frontend

React 19, TypeScript strict, Vite, React Router, TanStack Query, Tailwind CSS 4,
Lucide React и Fetch API. Интерфейс на русском языке, адаптирован для телефона.

## Запуск

Требуется Node.js 22.12+ и npm.

```sh
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173. Без действующей сессии приложение направляет на
`/login`. Аккаунт создаётся администратором на стороне Go; демонстрационных
учётных данных и mock backend нет.

API должен быть запущен отдельно на `http://localhost:8080` с PostgreSQL.
Frontend не запускает Go, Python или миграции. Сервер сам не читает `.env`:
его переменные нужно передать процессу согласно `../docs/auth.md`.

Для локального Go нужны:

```dotenv
APP_ENV=development
COOKIE_SECURE=false
ALLOWED_ORIGINS=http://localhost:5173,http://localhost:8080
```

Vite проксирует `/api` на `http://localhost:8080`, сохраняя исходный Origin.
Не смешивайте `localhost` и `127.0.0.1`. Все fetch-запросы относительные и
используют `credentials: "same-origin"`: cookie устанавливается на адрес
frontend через proxy. Origin validation не отключается, CORS `*` не нужен.

## Страницы и контракты

- `/login`: вход, ошибки, восстановление сессии через `GET /auth/me`.
- `/chat`: новый диалог, примеры вопросов, поиск, точные фрагменты источников.
- `/chat?session=<uuid>`: сохранённый диалог, архивирование.
- `/documents`: список с пагинацией, версии, статусы, скачивание активного
  оригинала; для admin — загрузка PDF/DOCX/TXT.
- `/`: переход в защищённый `/chat`, затем `/login`, если сессия отсутствует.
- Неизвестный адрес: страница 404.

Base URL — `/api/v1`. Типы сверены с `../docs/auth.md`, `search.md`, `chat.md`,
`documents.md`, `versioning.md` и Go handlers/domain.

Подключены:

| API                                                     | Назначение                               |
| ------------------------------------------------------- | ---------------------------------------- |
| POST `/auth/login`, GET `/auth/me`, POST `/auth/logout` | Cookie-сессия                            |
| POST `/search`                                          | Поиск без серверной истории              |
| GET/POST `/chat/sessions`                               | История и создание диалога               |
| GET/DELETE `/chat/sessions/{id}`                        | Чтение и архивирование                   |
| POST `/chat/sessions/{id}/messages`                     | Сохранённый поиск                        |
| GET/POST `/documents`                                   | Список и multipart загрузка              |
| GET `/documents/{id}`                                   | Активная и последняя версия              |
| GET `/documents/{id}/versions`                          | Последняя версия при отсутствии активной |
| GET `/documents/{id}/download`                          | Активный оригинал                        |
| GET `/documents/{id}/versions/{versionId}/download`     | Именно процитированная версия            |

Список документов не содержит объектов версий: для каждой видимой строки
запрашиваются метаданные. Пока активной версии нет, используется список версий,
поскольку endpoint метаданных в текущем Go возвращает в этом случае 404.
Отправка файла не означает готовность к поиску: обработка и публикация выполняются
backend. Кнопка «Обновить» повторно получает список и метаданные версий;
они также обновляются при возврате на вкладку или повторном открытии страницы.

Номера страниц, разделы, версии и тексты выводятся только из API. Пропущенные
метаданные не дополняются. `score` не показывается как достоверность. Нулевые
результаты Search API (у него всегда `mode: "search"`) отображаются как состояние
«Информация не найдена». Режимы Chat API имеют отдельные метки: `generated` —
«Ответ AI», `clarification` — «Уточняющий вопрос», `search` — «Поиск по документам»,
`no_sources` — «Информация не найдена». Пояснение об отсутствии генерации
показывается только для `search`.

Отсутствие sources не считается признаком изменения ACL. При отзыве доступа
интерфейс выводит безопасный заменяющий текст, который вернул сервер, сохраняя
исходный mode. Закрытое содержимое не восстанавливается из предыдущих ответов.
При повторном открытии диалога история заново запрашивается у API.

## Chat API и fallback

В текущей рабочей копии Chat API уже описан и реализован, поэтому подключён по
существующим DTO. Список диалогов запрашивается страницами по 20; история —
последовательными страницами по 100 в хронологическом порядке. React Query
отменяет чтение при уходе со страницы. Текущая отправка также отменяется при
уходе; при обрыве после серверного commit история может уже содержать результат.

Если **список** `/chat/sessions` возвращает 404/405/501, доступен Search API:
сообщения остаются только в React state и явно отмечены как временные. Переход
на другую страницу или перезагрузка их сбрасывает. 401/403/500/503 и сетевые
ошибки не маскируются fallback. Неизвестный ID сохранённого диалога также
показывает ошибку, не подменяется временным чатом.

Новая серверная сессия создаётся при первом вопросе. При повторе неудачной
отправки сохраняются ID созданного диалога и `client_message_id`, что позволяет
без дублирования получить результат после потери ответа. Автоматических повторов
изменяющих запросов нет; текст вопроса сохраняется при ошибке.

После появления Chat API на запущенном сервере нажмите «Проверить снова» в
истории либо перезагрузите страницу. Если контракт останется как в `docs/chat.md`,
изменения frontend не нужны. При изменении DTO обновите `src/types/api.ts` и
`src/api/chat.ts`. Все четыре текущих режима (`search`, `no_sources`, `generated`,
`clarification`) поддержаны в типах и отображении. Уточняющий вопрос не блокирует
отправку следующего сообщения.

## Безопасность и ограничения

- HttpOnly session cookie не читается. CSRF берётся из `ai_csrf` или
  `__Host-ai_csrf`, передаётся в `X-CSRF-Token` для POST/PATCH/DELETE.
- Нет localStorage/sessionStorage, сохранения паролей, журналирования секретов,
  HTML-вставок из документов и вымышленных ответов.
- После успешного logout запросы отменяются и Query cache очищается.
  При 401 защищённого endpoint интерфейс сбрасывает сессию и закрывает страницы.
- Серверный текст ошибок не выводится: используются безопасные русские сообщения.
- Отображение формы admin — удобство интерфейса. Все проверки ролей и ACL
  выполняет Go. Загруженные источники не персистируются; при фокусе окна
  сохранённый диалог перечитывается с актуальным ACL.
- Готовые bundle-файлы находятся в `dist/`. Production-хост должен отдавать
  `index.html` для клиентских маршрутов и проксировать `/api` на том же origin;
  backend требует HTTPS и secure cookies в production. `vite preview` только
  для просмотра сборки, API proxy в нём не настроен.

Генеративные ответы и уточняющие вопросы отображаются из Go Chat API; frontend
сам не вызывает LLM. PDF viewer, ACL UI, управление пользователями, редакторы,
streaming, деплой и инфраструктура не реализованы.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
npm run build
```

Vitest проверяет CSRF/cookie transport, FormData без ручного Content-Type,
401 и безопасные ошибки, пустые ответы, AbortSignal, пагинацию истории,
ключ идемпотентности, условия fallback, отображение четырёх режимов и замену
закрытого содержимого актуальным серверным текстом при обновлении истории.
Это frontend-тесты с подменённым fetch,
а не проверка реального Go API.

Для ручной интеграционной проверки с запущенным Go: войти → перезагрузить
`/chat` → отправить вопрос → открыть сохранённый диалог → скачать источник →
открыть базу знаний → загрузить документ под admin → выйти → проверить, что
прямой `/documents` снова переводит на `/login`. Под member проверить отсутствие
формы загрузки и список только разрешённых документов.
