## Retrieval: реальные результаты

FTS — настоящий `POST /api/v1/search` текущего Go image, со всеми существующими
эвристиками/strict-relaxed SQL. Semantic — exact cosine, 384 L2-normalized values,
`query: ` / `passage: `, title + исходный content. Hybrid — FTS + semantic через RRF.

| Набор | Метод | Recall@5 | Recall@10 | MRR | Строгая evidence precision |
|---|---|---:|---:|---:|---:|
| Development | FTS | 25% | 25% | 0.250 | 100% |
| Development | Semantic | 100% | 100% | 0.906 | 8.5% |
| Development | Hybrid + RRF | 100% | 100% | 0.906 | 8.5% |
| Holdout | FTS | 20% | 20% | 0.200 | 100% |
| Holdout | Semantic | 90% | 90% | 0.813 | 7.7% |
| Holdout | Hybrid + RRF | 90% | 90% | 0.813 | 7.7% |

Recall учитывает **все** gold chunks составного вопроса. Precision — micro precision
минимальных подтверждающих chunks среди всех кандидатов, включая негативные вопросы;
это намеренно строгая оценка доказательств, не тематической близости. Высокая precision
FTS достигается при очень малом числе результатов. Без порога e5 возвращает 10 кандидатов
на каждый вопрос, в том числе без ответа. Шапки таблиц/дополнительный правдивый контекст
не размечены как минимальные gold answers. Значения нельзя трактовать как precision
финальных цитат или качество после ещё не реализованного reranker.

Во всех 46 вопросах **ordered candidate IDs Semantic и Hybrid совпали**. Здесь FTS
не добавляет уникальных релевантных источников к e5. Разницу в генерации ниже нельзя
приписывать RRF. Улучшение e5 против FTS наблюдается на всех девяти тематиках, в том
числе каждой из пяти holdout-тематик; вопросы по двум документам учитываются в обоих
документных срезах. Подробности — `per-document.json`.

| Тема | FTS Recall@10 | Semantic Recall@10 |
|---|---:|---:|
| Командировки | 25% | 100% |
| Учётные записи | 25% | 100% |
| Закупки | 25% | 100% |
| Резервные копии | 25% | 100% |
| Лаборатория, holdout | 0% | 75% |
| Эвакуация, holdout | 25% | 75% |
| Договоры, holdout | 20% | 100% |
| Стандарт поддержки, holdout | 40% | 100% |
| Премиальная поддержка, holdout | 25% | 100% |

На development top-1 cosine положительных вопросов: **0.805–0.888**; отрицательных:
**0.808–0.840**. Диапазоны перекрываются. Один глобальный порог без оценки ложных
совпадений не решает задачу; глобальный FTS relevance threshold не менялся.

## Ответы и цитаты: проверка содержания, не generated mode

В финальном прогоне проверено 138 ответов: 46 вопросов × 3 arms. FTS проходит
настоящий Chat API. Experimental arms передают свои top-8 в тот же неизменённый
private Python RAG/Qwen. Это offline сравнение кандидатов, не готовая интеграция
ChatService. Выводы generation проверены агентом по исходному тексту и цитируемым
IDs; это не независимая экспертная оценка. Критерий строгий: все запрошенные части
ответа должны присутствовать, каждое содержательное утверждение подтверждаться.

| Holdout, 20 положительных + 6 отрицательных | FTS | Semantic | Hybrid |
|---|---:|---:|---:|
| Полностью grounded ответы на положительные | 4/20 = 20% | 16/20 = 80% | 17/20 = 85% |
| Полностью подтверждённые набором цитат положительные ответы, среди выданных | 100% | 94.1% | 94.4% |
| Цитируемые UUID действительно были во входном allowlist | 100% | 100% | 100% |
| Выдуманные запрошенные факты на негативных | 0/6 | 0/6 | 0/6 |
| `answered` на негативных вместо abstention | 0/6 | 1/6 | 1/6 |

На development grounded accuracy: FTS 4/16, Semantic 16/16, Hybrid 16/16.
Выдуманных значений на четырёх негативных вопросах нет. Hybrid при этом один раз
выдал `answered`, прямо сообщив, что имя аналитика SOC отсутствует.

**Найденная ошибка генерации h09:** оба experimental arms правильно называют семь
лет хранения, но затем добавляют «после этого срока» для передачи оригиналов в архив.
Источник требует передачи в течение 30 дней после закрытия договора, не после семи
лет. Оба ответа засчитаны как incorrect/ungrounded, несмотря на правильную первую
фразу и реальные цитаты. Текущий RAG не изменён по ограничению пользователя.

**Негативы:** `answered` на вопрос о ФИО заведующего лабораторией содержит явное
«имя не указано», без выдуманного ФИО. Поэтому фактический FAR = 0/6, но protocol
abstention rate не идеален. Это разные метрики; ноль на шести вопросах не доказывает
нулевой FAR в эксплуатации.

**Разделение этапов ошибки:** h06 («кабина подъёмника») имеет правильный источник
в обоих одинаковых candidate lists. В Semantic-вызове Qwen вернул insufficient,
в Hybrid-вызове — правильный запрет. Это вариативность generation при одинаковом
retrieval, не выигрыш RRF. В предварительном диагностическом прогоне h04 также
наблюдался HTTP 502 `llm_invalid_response`; финальный исправленный прогон завершил
138/138 без HTTP errors. Предварительная ошибка не объявляется retrieval-пропуском.

Raw outputs: `answers.json`.
Содержательная разметка: `review.json`,
агрегаты: `review-summary.json`.

## Latency и ресурсы

| Holdout retrieval | p50 | p95 |
|---|---:|---:|
| FTS, loopback HTTP + Go + PostgreSQL | 4.07 ms | 4.55 ms |
| Semantic, tokenizer + ONNX + exact scan | 5.44 ms | 7.67 ms |
| Hybrid, последовательная сумма + RRF | 9.57 ms | 11.69 ms |

Три warm измерения на вопрос, затем p50/p95 медиан. Hybrid здесь **расчётная сумма
измеренных этапов**, не latency существующего hybrid HTTP endpoint. Разные process/
network boundaries указаны явно; это не симуляция production network.

Generation/Chat p50/p95 на holdout: FTS **17 ms / 2.40 s** (большинство запросов сразу
no_sources), Semantic **4.11 / 7.01 s**, Hybrid **4.09 / 6.93 s**. Сравнение выполнялось
с двумя одновременными запросами Qwen; эти интервалы включают локальные request/response
накладные расходы. Планирование/reranking не добавлялись, их будущая latency неизвестна.

| Локальный CPU e5 | Значение |
|---|---:|
| Model load | 1.04 s |
| Индексация, включая load | 1.48 s для 32 chunks |
| Peak RSS индексации | 1074 MiB |
| Peak RSS query experiment, включая load | 1082 MiB |
| RSS после прогрева | около 778 MiB |
| CPU за query experiment | 2.69 CPU s / 1.89 wall s, около 142% одного core |
| Vector array | 49 280 bytes, 32 × 384 FP32 + .npy header |
| Веса ONNX на диске | 470 268 510 bytes |

ONNX ограничен двумя intra-op threads и одним inter-op thread. Host — Windows,
12 logical CPUs / 32 GiB RAM. Это **не нагрузочный тест VPS 2 vCPU / 4 GiB**.
Последний idle Docker snapshot после restart: Go 26.5 MiB, Python 63.4 MiB, PostgreSQL
28.9 MiB; это не их peak под нагрузкой. Нельзя складывать эти idle числа и считать
доказанной production ёмкость. По маленькому корпусу нельзя выбирать HNSW.

## 512 токенов, ACL и E2E-проверки

Prefix formatting проверяется на равенство полной строке. Исходная вспомогательная
реализация добавляла XLM-R space token при отдельном кодировании trailing space;
тест нашёл ошибку. Она исправлена, vectors/metrics/generation пересчитаны; первые
диагностические цифры не используются в финальной таблице. Корпус, ground truth,
RRF k/top-k не менялись, эвристики по holdout не подбирались.

В самом корпусе все 32 embeddings укладываются в одно окно. Дополнительный
изолированный long-context probe: 2267 content tokens → 5 окон, каждое ≤512 с
префиксом/BOS/EOS, overlap 64; tail включён. Правило в хвосте даёт лучший cosine в
последнем окне (0.810 против примерно 0.761–0.763 в предыдущих). Это проверка отсутствия
усечения, не оценка Recall. Overlong query отклоняется явно, исходный chunk ID сохранён.

SQL snapshot перед embeddings и generation включает текущего активного member,
document ACL, active_version и ready непосредственно в SQL. Пример:

```sql
FROM document_chunks c
JOIN document_versions v ON v.id = c.document_version_id
JOIN documents d ON d.id = v.document_id AND d.active_version_id = v.id
JOIN users u ON u.id = :trusted_user_id AND u.is_active AND u.role = 'member'
WHERE v.status = 'ready'
  AND EXISTS (SELECT 1 FROM document_access a
              WHERE a.document_id = d.id AND a.user_id = u.id)
```

Закрытый документ и historical version не кодировались и не передавались Qwen.
Memory snapshot не предлагается как production ACL cache: перед compare/answers
изменение snapshot вызывает отказ. В будущей интеграции каждую semantic/FTS ветку
нужно выполнять в SQL с текущими проверками, не фильтровать запрещённый global top-k
после поиска. Действующий GIN и его SQL не менялись.

Проверено на настоящих отдельных контейнерах:

- 9 разрешённых download URLs возвращают оригинальные файлы с совпадающим SHA256;
  закрытый документ возвращает 404.
- Отзыв ACL удаляет документ из SQL snapshot и прямого Search API; возврат
  восстанавливает видимость.
- Варианты вопроса о закрытом сейфе и старом тарифе не получают закрытых/старых
  source IDs и не приводят к выдуманному коду.
- При остановленном Python Go FTS работает; Chat сохраняет `search` fallback с
  настоящими источниками; повтор client_message_id возвращает тот же turn.
- После restart экспериментальных PostgreSQL/Go сохраняются chunk IDs, сессии,
  видимость и результат поиска.
- Существующие service/repository Search/RAG tests проходят на отдельной тестовой
  PostgreSQL, включая SQL ACL/active-ready/version checks. Новые experiment tests:
  **12 passed**, в том числе реальная e5 tokenization, window coverage, cosine/RRF
  deduplication и метрики составных вопросов.

Метаданные проверки: `security-checks.json`.
Тестовые контейнеры после работы остановлены, данные и вектора сохранены локально;
основной стек продолжает работать.

## Решение по внедрению

Есть основание для pilot semantic candidate retrieval: Recall растёт и на development,
и на каждой новой holdout-тематике. Но этот набор мал, все документы синтетические,
негативов только 10, и финальная точность ответа ниже retrieval recall. Не доказаны
масштабируемость, многопользовательская нагрузка или преимущество RRF над одним e5.

Следующий отдельный план: аддитивная pgvector migration после 00007, model/index
revision + per-version readiness, контролируемая durable индексация/reindex, exact SQL
с ACL, feature flag и FTS fallback; затем bounded planner для standalone follow-up,
RRF/diversity, reranker/evidence gate и структурное table expansion после отбора.
Полный SQL-подход и acceptance gates — [integration-plan.md](integration-plan.md).
Нужны новый не просмотренный holdout и измерения на целевом Linux VPS до включения.
