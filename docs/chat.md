# Chat API: поиск с сохраняемой историей

ChatService вызывает существующий SearchService через DI, без HTTP-запроса к
собственному Search API. По умолчанию RAG отключён и Python для чата не требуется.
Опциональная генерация описана в [Go → Python RAG](rag.md). Поиск использует
только нормализованное текущее сообщение; история не используется для
переписывания запроса. Например, «А какой срок?» может не найти источников.

## Endpoints и авторизация

| Метод | Путь | Успех |
| --- | --- | --- |
| POST | `/api/v1/chat/sessions` | 201, созданный диалог |
| GET | `/api/v1/chat/sessions?limit=20&offset=0` | 200, список своих активных диалогов |
| GET | `/api/v1/chat/sessions/{id}?limit=20&offset=0` | 200, диалог и страница истории |
| POST | `/api/v1/chat/sessions/{id}/messages` | 200, сохранённая пара сообщений с источниками |
| DELETE | `/api/v1/chat/sessions/{id}` | 204, архивирование |

Все endpoints используют существующий RequireAuth и HttpOnly `ai_session` cookie.
Изменяющие запросы требуют разрешённый `Origin` и `X-CSRF-Token` текущей сессии.
JSON-запросы требуют `Content-Type: application/json`. Лимит тела — 4096 байт;
неизвестные поля и несколько JSON-значений отвергаются. Клиент не задаёт
`user_id`, `role`, режим ответа или список источников.

Нет cookie / истёкшая сессия / выключенный пользователь → 401; неверные CSRF или
Origin → 403; чужой или неизвестный диалог → 404, **включая admin**. Неверный
UUID пути также даёт 404. Все ответы получают `Cache-Control: no-store`.

## Создание и чтение

Создание принимает `{}` либо `{"title":"Согласование документов"}`. Пустой
заголовок после TrimSpace заменяется на «Новый диалог». Максимум — 200
Unicode-символов до нормализации, без NUL, валидный UTF-8. Пустое тело и `null`
недопустимы.

Объект диалога содержит `id`, `title`, `created_at`, `updated_at`, `archived_at`
(null до архивирования). Владелец определяется по аутентифицированному
пользователю и не включается в ответ.

Список возвращает `{"sessions":[...],"limit":20,"offset":0}`. Сортировка:
`updated_at DESC, id`; архивированные диалоги исключены. История возвращает:

```json
{
  "session": {"id":"<uuid>","title":"Новый диалог","created_at":"<RFC3339>","updated_at":"<RFC3339>","archived_at":null},
  "messages": [
    {"id":"<uuid>","session_id":"<uuid>","role":"user","content":"согласование","mode":null,"client_message_id":"<uuid>","created_at":"<RFC3339>","sources":[]},
    {"id":"<uuid>","session_id":"<uuid>","role":"assistant","content":"Найдены подходящие положения инструкции.","mode":"search","reply_to_id":"<user message uuid>","created_at":"<RFC3339>","sources":[]}
  ],
  "limit": 20,
  "offset": 0
}
```

Это форма DTO, а не реальные данные. Источники описаны ниже. Пустые коллекции
возвращаются как `[]`. Пагинация ограничивает **сообщения**, поэтому страница
может разделить пару user/assistant. Порядок истории хронологический, по
внутреннему монотонному `position`, без зависимости от совпадающих timestamps.
Для обоих GET: `limit` по умолчанию 20, диапазон 1–100; `offset` 0–1 000 000.
Ошибки границ и повторяющиеся параметры дают 400. Общий COUNT не вычисляется.

Архивирование идемпотентно, сохраняет историю и первый `archived_at`. Владелец
может открыть архивированный диалог по ID, но отправка, включая повтор старого
ключа, возвращает 409 `chat session is archived`.

## Отправка и ответ

```json
{
  "content": "Как согласовать служебную записку?",
  "client_message_id": "de643dba-2d89-438c-aa7a-1ef5081e65b7"
}
```

Обязательны непустой UUID ключа и валидная UTF-8 строка без NUL, максимум 500
Unicode-символов **до** TrimSpace. После TrimSpace строка не должна быть пустой.
Границы совпадают с SearchQuery. Поиск использует стандартный лимит 10 источников
и существующую Russian FTS/ACL/active-ready фильтрацию SearchService.

Успешный ответ (иллюстративные значения):

```json
{
  "user_message_id": "<uuid>",
  "assistant_message_id": "<uuid>",
  "mode": "search",
  "message": "Найдены подходящие положения инструкции.",
  "sources": [
    {
      "chunk_id": "<uuid>",
      "document_id": "<uuid>",
      "document_version_id": "<uuid>",
      "document_title": "Инструкция",
      "version_number": 2,
      "chunk_index": 3,
      "content": "Текст сохранённого фрагмента",
      "page_number": null,
      "section_number": null,
      "section_title": null,
      "score": 0.25,
      "position": 1
    }
  ],
  "user_created_at": "<RFC3339>",
  "assistant_created_at": "<RFC3339>"
}
```

При отсутствии результатов: `mode: "no_sources"`,
`message: "В доступных документах не найдена информация для ответа."`,
`sources: []`; остальные поля сохраняются. `score` — сохранённая релевантность
PostgreSQL, не вероятность правильности. Метаданные цитат читаются из реальных
документов/версий/фрагментов, неизвестные страницы и разделы остаются null.
`position` начинается с 1 и сохраняет порядок исходной выдачи. Поля источника
повторно используют SearchResult; `storage_key` не возвращается.

## Атомарность и повторные запросы

`client_message_id` уникален в пределах диалога. Повтор с тем же нормализованным
content возвращает исходные IDs, текст и timestamps без добавления сообщений.
Повтор с другим нормализованным content даёт 409
`client_message_id already used with different content`. Для нового сообщения
нужен новый ключ. Сбой SearchService возвращает 500 и не сохраняет сообщений.

Поиск выполняется без открытой транзакции. После поиска короткая транзакция
блокирует строку **принадлежащего владельцу** диалога, повторно проверяет архив
и ключ, сохраняет user + assistant + источники и обновляет `updated_at`.
Пара сохраняется целиком либо не сохраняется вовсе. Уникальные ограничения БД
и блокировка защищают также от конкурентных запросов к разным Go-процессам.
Конкурентные повторы могут выполнить лишний поиск, но сохранят одну пару.

Перед записью каждого источника повторно проверяются существование ready-версии
и актуальный ACL. Если источник исчез или доступ изменился между поиском и
записью, вся пара откатывается: 409 `sources changed; retry the message`.
Клиент может повторить запрос с тем же ключом. После commit ответ заново
загружает источники с текущими правами. Если сеть или контекст запроса оборвутся
после commit, повтор ключа позволяет получить уже сохранённый результат.

## История, ACL и версии

Миграция [00006_chat.sql](../migrations/00006_chat.sql) создаёт `chat_sessions`,
`chat_messages`, `chat_message_sources`, ограничения ролей/режимов, FK и индексы.
В источниках хранятся только ID, позиция и ранг. В режимах search/no_sources
assistant.content содержит фиксированное общее сообщение. Для generated и
clarification миграция 7 добавляет отдельные зависимости и защиту всего текста
при отзыве ACL; см. [правила RAG](rag.md).

Каждый запрос репозитория ограничен владельцем, даже для admin. Загрузка
источников дополнительно соединяет текущего активного пользователя с документом
и проверяет его **текущую роль и ACL в SQL**. До Go не доходит ни текст, ни
идентификаторы, ни название закрытого источника. Это действует для истории,
повтора client_message_id и RecentMessages. Исторические версии разрешены лишь
после той же проверки текущих прав документа, без подмены на новую active-версию.

После отзыва доступа исходный `mode: search`, текст ответа и IDs сообщений
сохраняются, но закрытые sources исключаются, вплоть до `[]`. Исходные позиции
могут иметь пропуски. При повторной выдаче доступа сохранённые ссылки снова
доступны. Собственный текст вопроса пользователя сохраняется без изменений;
приложение не может отозвать копию документа, уже полученную клиентом ранее.

Реальный FK `chunk_id → document_chunks(id) ON DELETE RESTRICT` сохраняет старые
цитаты. Существующий ReplaceVersionChunks удаляет прежние chunks, поэтому
переиндексация **уже процитированной версии** отклоняется БД и полностью
откатывается. Нельзя удалять ссылки или перенаправлять их на новые chunks:
для обновления такого документа создавайте новую версию. Непроцитированные
версии и обычный ingestion работают как прежде. Миграции 1–5 и ingestion-код
не менялись; Down миграции 6 удаляет только таблицы чата.

## Расширение и проверка

`ChatService.RecentMessages(ctx, actor, sessionID, limit)` возвращает максимум
100 последних сообщений в хронологическом порядке с проверкой владельца и ACL.
При включённом RAG история дополнительно ограничена RAG_MAX_HISTORY_MESSAGES
(по умолчанию 10), общим бюджетом контекста и безопасностью зависимых ответов.
Генератор передаётся через ChatGenerator DI; существующий search fallback,
пути, request DTO и форма `message`/`sources` сохраняются. Новые режимы:
generated и clarification. Подробный протокол и проверки — в [rag.md](rag.md).

Zap записывает создание/архивирование, ошибки обработки без текста зависимостей,
продолжительность поиска, успех и число источников. Вопросы, названия/тексты
документов, cookies и токены в эти записи не попадают.

Новые файлы: три domain-модели `chat*.go`, postgres/chat_repository.go,
service/chat.go, handlers/chat.go, их unit/HTTP/PostgreSQL и сквозные тесты,
эта документация и миграция 6. Изменены cmd/server/main.go и HTTP router для DI,
два существующих PostgreSQL-теста для последовательного rollback миграций.

Проверки: `go mod tidy`, `go test ./...`, `go vet ./...`,
`go build ./cmd/server`; дополнительные race-проверки затрагиваемых слоёв.
PostgreSQL-тесты требуют отдельный `TEST_DATABASE_URL` с БД, заканчивающейся
на `_test`, и создают собственные изолированные схемы. Python/LLM не нужны.
Тесты покрывают атомарный rollback пары, concurrent idempotency, архивирование
и отзыв ACL во время поиска, сохранение истории при пересоздании сервисов,
пагинацию, исторические версии, отмену переиндексации процитированных chunks,
чужие диалоги (включая admin), cookie/CSRF/Origin и отсутствие секретов в логах.
