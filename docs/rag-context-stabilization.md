# Стабилизация контекстного RAG — 25.10.2026

Последующая проверка полноты и уточнений отклонена; отчёт и кандидат вынесены
во внешний архив: [уборка репозитория](repository-cleanup-report.md).
Новый кандидат Generator/Gate отклонён; исторические результаты ниже сохранены.

Контрольный дефект отсутствия доступных документов воспроизведён и исправлен.
На новом независимом наборе результат вырос с **19/27 до 23/27**, без новых
ошибок относительно baseline в этом прогоне. Однако критерии допуска целиком
не выполнены: генератор всё ещё задаёт одно ненужное уточнение и пропускает
часть значимых положений. `CONTEXT_RESOLVER_ENABLED=false` сохранён.
Отклонённый режим стиля впоследствии удалён при уборке. Основной React Chat
и основные Docker-сервисы не обновлялись.

## Точная причина контрольной ошибки

Изучены [первоначальный аудит](rag-dialogue-context.md),
[предыдущая доработка и её оценка](rag-context-improvements.md), сохранённые
артефакты экспериментов, Resolver, AIClient, ChatService, Semantic Search,
генерация и тесты ACL/provenance.

Старое сообщение `no-candidates handling <nil>` было сообщением `t.Fatal`
в контрольном тесте. `<nil>` относилось к ошибке `SendMessage`; проверка также
требовала `mode=no_sources` и отсутствие цитат. Это сообщение само по себе
не доказывает panic приложения. Фактический ответ исторического context-контроля
не был записан до остановки теста; восстановить именно тот ответ нельзя.

Для воспроизведения использована сохранённая в отдельном style-контроле
ошибочная формулировка Resolver о разных трактовках явно названного предмета.
Она повторена детерминированно, без нового инференса, через настоящий ChatService,
SQL visibility, историю и сохранение результата в отдельной временной БД.
До исправления оба случая — пустая БД документов и наличие только закрытого
документа — завершились успешным `SendMessage`, пустыми цитатами и ошибочным
уточнением. Падал assertion теста, а не приложение.

Механизм ошибки:

1. Resolver предлагал предварительный `needs_clarification`.
2. Поиск возвращал пустой список без ошибки. `[]SearchResult` не сообщал,
   отсутствуют ли кандидаты или Gate отклонил существующих кандидатов.
3. ChatService при любом пустом списке оставлял предварительное уточнение.
4. При пустой истории свободный текст уточнения не проверялся на якоря,
   применявшуюся к альтернативам из истории, и мог содержать придуманные варианты.

Воспроизведение до исправления сохранено в
`.local-integration/rag-stabilization/reproduction-before.txt`.

## Изменённые компоненты

### Типизированный результат поиска

В `internal/domain/search.go` добавлен внутренний `RetrievalResult` с источниками
и `RetrievalDisposition`: `available`, `no_candidates`, `evidence_rejected`.
Непустой список допустим только для `available`; неизвестное состояние или
несогласованная комбинация не превращаются в успешный пустой ответ.

`SearchService.SearchForChat` передаёт этот результат по существующему поисковому
пути. Публичные `Search` и `SearchContext` сохранили прежний контракт и используют
ту же реализацию. Нового endpoint, Resolver или Query Planner нет. При ошибке
источники отбрасываются целиком, как и до рефакторинга.

ChatService с включённым существующим флагом проверяет типизированное состояние:

| Результат поиска | Поведение |
| --- | --- |
| Нет кандидатов, в том числе только закрытые документы | `no_sources`, предварительное уточнение не сохраняется |
| Кандидаты есть, Gate не подтвердил сведения | `no_sources`; допустимо оставить только валидное предварительное уточнение о настоящей неоднозначности |
| Gate подтвердил источники | Прежняя генерация с проверкой source IDs |
| Техническая ошибка и пустой degraded fallback | `search_unavailable` / HTTP 503, без фиктивного ответа об отсутствии сведений |
| Отсутствующее/невалидное типизированное состояние | `search_unavailable`, ответ не сохраняется |

Отсутствие кандидатов имеет приоритет: уточнять предмет при отсутствии какого-либо
поискового материала бесполезно. Это относится и к неоднозначному вопросу при
пустом пуле. При наличии кандидатов настоящее отсутствие предмета может вызвать
одно уточнение; отсутствие цены, санкции или другого неизвестного факта само
по себе его не создаёт. Наружу причина отсутствия кандидатов по ACL не раскрывается.

### Контракт уточнений Resolver

В существующем приватном ответе добавлен `clarification_kind`:

- `missing_subject`: только пустая разрешённая история и отсутствие альтернатив;
  сервер формирует один нейтральный вопрос о предмете/процессе.
- `choice`: ровно две различные дословные альтернативы из текущего вопроса
  (индекс `-1`) или разрешённой истории; сервер формирует вопрос о выборе.

Произвольный модельный текст вопроса запрещён: на входе допустим `null` либо
точный серверный вариант. Нельзя спрятать выдуманные альтернативы в строке
`clarification_question`, в том числе при пустой истории. Go повторяет проверку
канонической формулировки, вида уточнения и якорей; Python не является единственной
границей доверия. Общая серверная формулировка — часть протокола, не готовый ответ
или исключение для конкретного предмета.

`QueryPart` в Go теперь отвергает отсутствующий или `null` индекс: он больше
не может незаметно превратиться в индекс `0`. Отвергаются отсутствующая/пустая
цитата, неверные индексы и неизвестные поля якоря. У успешного HTTP-ответа Resolver
обязательно положительное число model calls. Невалидные планы по-прежнему
возвращают прежний Semantic Search, без дополнительной попытки Qwen.

Go и Python нужно обновлять согласованно: приватный контракт расширен.
При несовместимой версии строгая валидация приводит к прежнему поисковому
fallback; отключать её для смешанных версий не следует.

Изменение промпта Resolver связано с этим типизированным контрактом: вопрос
рисует сервер, незнакомое имя уже названного предмета не означает отсутствия
предмета. В код не добавлялись названия документов, синонимы и ответы для
контрольных вопросов. Генератор и его промпт, включая кандидат стиля, **побайтово
совпадают со снимком до этой стабилизации**.

Проверка якорей остаётся структурной. Она не доказывает правильность выбора
предмета моделью: в реальном прогоне Resolver иногда выбирал целый старый ответ.
Пустую историю также нельзя механически оценить на смысловую неоднозначность
одной проверкой JSON. При отсутствии доказательств допустимости план отклоняется;
полную семантическую корректность это не гарантирует.

## Новый независимый набор

Просмотренный v2 holdout не использовался для настройки. Перед первым новым
вызовом Qwen зафиксированы `corpus-v3-stabilization-holdout.json`, его SHA-256
и ожидания: пять новых разрешённых документов, восемь разрешённых фрагментов,
один закрытый документ, четыре отдельные сессии, **27 вопросов**.
Темы: удалённый доступ, вечерние встречи, выпуск каталога, восстановление
учётной записи и незаполненный шаблон согласования.

Baseline — тот же Go-путь с Resolver off и исходный Python из снимка до
стабилизации; context — Resolver on. Это сравнение off/on, а не повторное
измерение старого кандидата Resolver. Флаг стиля false в обоих случаях.
Сравнение baseline намеренно использует тот же Go-код; это явно отражено
параметром `--same-go-baseline` и метаданными.

Реальные Go ChatService, PostgreSQL/pgvector, E5, Gate и Qwen; по одному прогону,
без замены неудачных ответов повторными попытками. Код заморожен до инференса;
проверены хеши Python и Go, production-код после чтения результатов не менялся.
Отдельный контроль без доступа повторён как регрессионная проверка, не как
новая часть независимого набора. Контрольные ответы теперь записаны полностью.

Все 54 ответа просмотрены вместе с цитатами и ожиданиями. Разметка агента
находится в `review.json`; это не независимая человеческая экспертиза. Общий
балл требует правильного статуса, полноты, уместного уточнения и правильного
отказа. Отсутствие выдуманных утверждений не считается полным успехом.

| Метрика | Resolver off | Resolver on |
| --- | ---: | ---: |

Текст, индекс, документ и версия всех цитат проверены автоматически;
смысловое подтверждение — вручную. Source IDs проверяет существующий контракт.
Закрытый ключ не появился в ответах. Чужая сессия недоступна в обоих контролях;
тесты отзыва доступа и истории прошли. Необнаружение утечек в этой проверке
не является доказательством безопасности любого возможного диалога.

Улучшения:

- «Кто это подтверждает?» после подключения доступа теперь ссылается на
  руководителя подразделения вместо ложного отказа.
- После сравнения штатного сотрудника и подрядчика уточняется именно лицо,
  без возврата к старой теме публикации каталога.
- После «Для подрядчика» возвращаются 12 часов с момента активации, без
  повторного уточнения уже понятного предмета.
- «Какие действия требуются?» в новой сессии получает один вопрос о процессе;
  ответ о восстановлении учётной записи затем корректно используется.
- Понятное незнакомое название сети и вопрос о её стоимости получают честные
  отказы, а не выдуманные трактовки. Все семь вопросов без подтверждённых сведений
  обработаны без ложных уточнений.

Оставшиеся четыре ошибки, без настройки по результатам:

1. **Генерация:** на «На какой срок его выдают?» генератор получает фрагмент
   с обоими сроками доступа, но требует выбрать тип сотрудника вместо ответа
   с двумя условиями. Resolver правильно восстановил предмет. Ошибка есть
   и в baseline; исправление no-candidates её не устраняет.
2. **Генерация:** на вопрос о продлении пропущена блокировка профиля после
   истечения срока, хотя источник передан. Новая подтверждённая заявка и запрет
   ожидать автоматического продления сохранены.
3. **Отбор доказательств:** для полного выпуска каталога нужны два фрагмента,
   но Gate передал первый; не названы запись допуска и публикация только после
   допуска. Наличие `generated` не скрывает неполноту. Пороги и правила Gate
   ради этой метрики не менялись.
4. **Генерация:** в ответе о пустом шаблоне лицо и дата честно обозначены пустыми,
   но не названо заранее включённое в ожидания условие подписания согласования.
   Это консервативная оценка полноты, не выдумка лица или даты.

На новом наборе нет ухудшений относительно baseline по этой разметке, но
необходимая полнота и отсутствие ложных уточнений ещё не достигнуты. Одного
малого прогона недостаточно для допуска в основной Chat.

## Основная БД и миграция 12

Фактическая основная схема проверена чтением: версия **11**, столбца
`chat_messages.starts_new_topic` нет. Миграция 00012 не изменялась и не применялась
к основной БД в этой задаче. Новая сборка Go всё ещё требует схему 12 даже при
выключенном Resolver. Основной образ не обновлялся и не запускался заново.

Миграция добавляет boolean с постоянным default false и ограничение:
маркер допустим только для пользовательских сообщений. Данных она не удаляет,
старые строки получают false. PostgreSQL 17 поддерживает быстрое добавление
постоянного default, но `ALTER TABLE` всё равно требует блокировку, а валидация
CHECK может читать таблицу. Поэтому обещать отсутствие блокировок нельзя.

Штатный Goose Up, его transactional/advisory-lock путь и проверка версии
сохранены. На отдельной БД выполнены штатные миграции и существующий тест
перехода 11 → 12 с сохранением старых сообщений и default false. Startup check
не ослаблен; `AUTO_MIGRATE=false` не позволит запустить несовместимую сборку.

Перед будущим разрешённым обновлением основного Docker нужно тем же новым
бинарником выполнить `migrate status`, `migrate up`, повторный `migrate status`
с настроенным соединением к основной БД и ограниченным `DB_MIGRATION_TIMEOUT`.
Не запускать обычный сервер вместо явной команды миграции. Затем проверить
версию 12 и наличие столбца; флаги остаются false. Это порядок будущего обновления,
не операция, выполненная сейчас: deploy запрещён заданием.

PostgreSQL volume не удалялся. `down -v`, commit, push и deploy не выполнялись.
Не менялись DOCX Template Generator, React Wizard и пользовательские документы.
Изолированные тестовые контейнеры удалены, основной Docker не перезапущен.
