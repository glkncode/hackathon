# Template Generator 2.0

Доработка существующего backend. Создаётся отдельный **проект**, без подписания, визирования и присвоения регистрационного номера. Исходники десяти документов изучены; см. `template-generator-v2-audit.md`. Инструкция маркирована как учебный пример; её действующая официальная применимость не утверждается.

## Регистрация и совместимость

Все прежние публичные endpoints сохраняются. Администратор регистрирует новый шаблон через `POST /api/v1/templates`:

```json
{
  "document_id": "<UUID загруженного оригинала>",
  "document_version_id": "<UUID конкретной версии>",
  "name": "Рабочая группа / профиль 2.0.2",
  "profile": {"profile_version": 2, "...": "полный объект из docs/template-profiles/v2/working-group.json"}
}
```

`profile` и `fields` в одном запросе запрещены. Используйте **полный** JSON профиля, без иллюстрационного `...`. Шаблон закрепляет профиль и версию исходника; обновление профиля означает новую регистрацию. В существующем шаблоне можно менять только доступность. Миграция `00010_template_profiles.sql` добавляет nullable `profile` и `generation_snapshot`; `00011_template_profile_integrity.sql` строго отклоняет SQL NULL/неполный envelope для v2. Строки v1 остаются с NULL. Миграции 00001–00009 не менялись.

`docs/template-profiles/working-group.json` остаётся массивом v1. У него прежние поля и поведение, включая сохранение служебных элементов модуля: новая нормативная очистка применяется только к явно зарегистрированным профилям v2. Уже введённые ответы не интерпретируются как другая схема. Новый v2 не запрашивает утверждение самого модуля (approval_person/date), поскольку соответствующая таблица удаляется по методическим рекомендациям.

Обычный неизвестный DOCX без полей `{{name}}` и без конфигурации при попытке регистрации возвращает HTTP 400 с `support_status: "needs_configuration"`. Загрузка и RAG доступны независимо. Старый режим простых плейсхолдеров поддерживается; он не объявляется нормативно проверенным модулем.

## Профиль

Формальная схема: `ai-service/app/templates/profile.py`. Проверенные экземпляры: семь JSON в `docs/template-profiles/v2/`. Текущая ревизия **2.0.2**, версия правил **2026-10-24.3**, совместимый engine **docx-profile/2.0.0**.

Объект содержит идентификаторы/версии, SHA-256 оригинала, поля, источники, bindings, conditional_blocks, repeaters, document_cleanup, numbered_paragraphs, rules, approval_route. SHA источника правила помещён в `source.version`, положение — в `source.section`; сведения о нормативной актуальности из SHA не следуют.

Типы v2: прежние text/multiline_text/person/date/person_list, а также choice (allowlist), text_list (упорядоченные имена), repeater (массив объектов с фиксированными item_fields). Для участников отдельно требуются должность, подразделение и имя; необязательное agreement содержит оговорку о согласовании внешнего участника. Для руководителей и иных одиночных лиц используется строка person с подсказкой по должности, подразделению и падежу; смысловая полнота проверяется человеком.

`required_if` и `visible_if` определяют применимые обязательные вопросы. Скрытые ранее введённые ответы сохраняются, но отключённые фрагменты их не используют. Их типы всё равно проверяются. Отмена акта требует вид, дату, номер и название. Контроль подписанта не требует отдельного контролирующего лица. Родительный/винительный падеж вида локального документа выбирается декларативно; произвольные названия и ФИО автоматически не склоняются.

Операторы: equals, not_equals, present, all, any, not, date_gte, date_lte, field_equals, field_not_equals, count_gt. Отсутствующее значение не считается неравенством. Типы сравнений проверяются при регистрации. Нет eval/exec, произвольных путей, SQL, шаблонного кода или сетевых запросов. Граф required_if/visible_if проверяется на циклы; глубина условия/текстового выражения до 8, суммарно до 1024 узлов конфигурации. Профиль до 192 КиБ; до 64 полей, 128 правил, 128 bindings, 16 диапазонов, 8 repeaters. Повторитель ограничен максимум 30 строками. Значения суммарно до 64 КиБ; HTTP JSON до 256 КиБ. Выход до 10 МиБ.

## Структурные операции

Перед inspect/render проверяются ZIP/XML, безопасность пакета, SHA оригинала, точное совпадение всех якорей и отсутствие пересекающихся замен. Индексы относятся к исходному `word/document.xml`, до любых изменений. Bindings заменяют только явно описанные диапазоны текста, в том числе разделённые runs; свойства параграфов и runs сохраняются. Условные фрагменты формируют варианты из фиксированного набора текстовых сегментов и значений полей.

Удаляются проверенная верхняя таблица утверждения **модуля**, параграф-маркер, диапазон примечаний/общих правил и привязанный пустой параграф-разрыв. Зоны регистрации и ЭП обязательно присутствуют в protected, их XML проверяется на неизменность. Гриф утверждения создаваемого документа не определяется эвристикой по слову «УТВЕРЖДАЮ».

Conditional blocks могут удалять диапазон соседних параграфов/элементов одного родителя. Для комитета синхронно выбирается фрагмент заголовка, удаляется пункт об отмене и меняется контроль 3→2. Для локального документа контроль 5→4; для ответственных за ДОУ — 6→5. Перенумерация ограничена перечисленными якорями с буквальными номерами. Word numbering properties не переписываются. Непроверенные поля перекрёстных ссылок не поддерживаются; это не универсальная перенумерация произвольного DOCX.

Повторитель клонирует строку-прототип, заполняет существующие ячейки и удаляет исходные переменные строки. Сохраняются widths/borders/alignment/tcPr/pPr/rPr и горизонтальные объединения. Профили явно включают `keep_rows_together` (cantSplit) и `repeat_header` (tblHeader) для читаемого переноса таблиц. Вертикально объединённые прототипы отклоняются, поскольку требуют отдельной конфигурации. Объёмный текст, превышающий физический размер страницы, всё равно требует проверки в редакторе.

Все ZIP-части, кроме `word/document.xml`, копируются побайтно, включая styles, numbering, headers/footers, PAGE, media и relationships. После render проверяются безопасность ZIP/XML, защищённые зоны и открытие через python-docx. Ничего не удаляется по сходству с пользовательским текстом. Тест с пользовательской фразой «Примечания по заполнению … [42]» подтверждает её сохранность.

## Валидация и отчёт

`POST /api/v1/template-drafts/{id}/validate` и прежний `/next-question` сохраняют ready, missing_fields, invalid_fields, next_question. Дополнительно возвращаются visible_fields, required_fields, checks, approval_route и версии. Каждый check содержит rule_id, category, source (name/version/section), description, result, method. Blocking с failed запрещает генерацию; warning/info/manual_review сами по себе не блокируют. `user_confirmed` означает ответ пользователя, а не исследованный файл или выполненную процедуру.

Правила v2 исполняет один Python engine и при валидации, и непосредственно перед render. Go проверяет типы транспортных значений, управляет ACL, revision и сохранением. Поэтому межполевые проверки и условные вопросы не расходятся между Go и Python. Корректная по типу, но противоречивая дата может сохраняться в черновике; generate возвращает 422 с источником правила до её исправления. Ошибочные типы/даты/неизвестные ключи не сохраняются.

ИС: дата ввода сравнивается с датой готовности; более ранняя дата допускается только при явном выборе исключения и заполненном основании. Фактическая допустимость основания остаётся ручной проверкой. Утверждение эксплуатационной документации, полномочия, ограниченность рабочей группы, согласие работников и независимость аудиторов не считаются доказанными по отсутствию/наличию строки в форме.

Approval route — рекомендация, а не выполненный workflow. В ней есть применимость и реквизиты строк, required_departments, conditional_departments, additional_departments. Источники — фактические внутренние строки 2/3/4/6/7 Матрицы; список строк обрабатывается совокупно. Отметка «Нет» не запрещает согласование. Дополнительные подразделения вводятся по затронутой компетенции. Общий маршрут, лингвистическая экспертиза и решение ответственного исполнителя сохраняются.

При успешной генерации ответ и `GET /api/v1/generated-documents/{id}` содержат `generation_snapshot`: полный профиль, **значения именно этой revision**, отчёт, engine_version, source_document_version_id, draft_revision, project_status=draft_project. Снимок хранится в той же транзакции, что метаданные файла. Последующее редактирование черновика не изменяет старый отчёт и файл. SHA результата есть в прежнем поле metadata.sha256. Отдельный report endpoint не требуется.

GET/list черновиков v2 вычисляют актуальную валидацию через Python и требуют доступности renderer. Скачивание уже готового результата и чтение сохранённого отчёта требуют только БД/storage и свежего ACL; работоспособность при остановленном Python проверена.

## Запуск проверок

```powershell
ai-service/.venv/Scripts/python.exe scripts/audit_template_sources.py
ai-service/.venv/Scripts/python.exe scripts/build_verified_profiles.py
go test ./...
go vet ./...
go test -race ./internal/domain ./internal/service ./internal/repository/postgres ./internal/aiclient
docker compose run --rm --no-deps -e EMBEDDING_TEST_MODEL_PATH=/models/e5-small -v 'D:/Projects/hackathon:/qa:ro' -w /qa/ai-service --entrypoint python ai-service -m pytest tests -q -rs -p no:cacheprovider
ai-service/.venv/Scripts/python.exe scripts/template_v2_e2e.py --restart
ai-service/.venv/Scripts/python.exe scripts/template_e2e.py --restart
ai-service/.venv/Scripts/python.exe scripts/template_regression_smoke.py
```

Интеграционные Go-тесты БД требуют **отдельной** TEST_DATABASE_URL с именем БД `*_test*`; используют свои временные схемы. Основную БД для тестового удаления схем не указывать. `--restart` кратковременно перезапускает локальные сервисы. Проверочные документы/отчёты остаются в игнорируемой `.local-integration/template-v2-e2e`; E2E создаёт помеченные синтетические учётные записи и документы.

## Ограничения

[React Wizard](template-wizard.md) реализован отдельным UI-этапом поверх этого backend; [результаты проверки](template-wizard-verification.md). Реальный workflow, ИИС ДО, физическое присоединение приложений, ЭП, регистрация, определение официальной актуальности, автоматическая проверка должностных обязанностей, универсальная грамматика и распознавание произвольного DOCX не входят в этап. Ссылка на приложение к локальному приказу сохраняется, но в отчёте явно указано, что сам файл не включён. Аналогично с актом передачи имущества. Комитет использует предусмотренный оригиналом блок ЭП: подписант сохраняется в карточке/снимке, без имитации текстовой подписи.

Для окончательной готовности конкретного проекта нужны ручные действия из его отчёта. React Wizard отображает условные поля и все категории отчёта через существующий backend-контракт. Перед демонстрацией полезны реальные согласованные демонстрационные значения и просмотр результата на целевой машине с её шрифтами.
