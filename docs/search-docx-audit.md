# Аудит четырёх вопросов по DOCX

Проверка 24.10.2026. До изменений вызваны действующие POST /api/v1/search и
Chat API в локальном приложении, для каждого вопроса — новый диалог без истории.
После изменений использованы изолированная PostgreSQL 17, production Go
router/services/repositories, неизменённый Python FastAPI и реальный Qwen из
настроенной конфигурации. Изменённый backend не развёртывался.

## Где терялись источники

| Вопрос | websearch_to_tsquery | Relaxed до исправления | Место потери |
| --- | --- | --- | --- |
| Кто входит в состав рабочей группы? | вход & соста & рабоч & групп | Вводный пункт содержит состав, рабоч, групп: совпали 2/4; сами роли находятся в других chunks | SQL и разорванный табличный контекст ingestion |
| Какие обязанности у руководителя рабочей группы? | как & обязан & руководител & рабоч & групп | После удаления рамки 3/3 | Не терялся: Search → Chat → Python → generated |
| За что отвечает секретарь рабочей группы? | отвеча & секретар & рабоч & групп | 3/4 = 75% < 80% | SQL coverage |
| Кто контролирует исполнение распоряжения? | контролир & исполнен & распоряжен | Пункт 6 содержит контрол: 2/3 < 80% | SQL, различие словообразовательных форм |

Strict возвращал 0 для всех четырёх естественных вопросов. Изначально relaxed
проходил только для руководителя. SearchService не удалял полученные SQL-строки;
ChatService не вызывал Python при пустом retrieval. Отбора правильного источника
после top-k не было: он отсутствовал уже до ранжирования/LIMIT.

## Изменения Go

- Strict сохранён; порог 80%, минимум два значимых понятия, веса и приоритет
  strict не понижены.
- Ограниченные грамматические рамки «за что отвечает»/«входит в состав» не
  требуют буквального присутствия глагола в источнике.
- Подтверждённые пары `соста/состав`, `контрол/контролир` расширяют индексный
  OR-tsquery. Покрытие считает уникальные понятия; повтор вариантов не повышает его.
- Совпавший нумерованный вводный пункт с двоеточием получает непосредственный
  табличный контекст: максимум 8 следующих позиций, та же версия и секция,
  без перехода через обычный абзац/другой блок. Каждый источник сохраняет реальный
  chunk_id и неизменённый content; соседние таблицы и подпись не присоединяются.
- Все ветви SQL повторяют user/role/ACL, active_version и ready. Диапазоны соседей
  используют существующий `(document_version_id,chunk_index)`, FTS — прежний GIN.
- Учтён пункт, заканчивающийся примечанием `[7]`, при скрытии ложного section_title.

При default Search limit=10 и RAG_MAX_SOURCES=8 таблица занимает 5 источников и
передаётся полностью. Тест проверяет точные индексы `[10,11,12,13,14]`, `[16]`,
`[17]`, `[19]`, их реальные IDs, тексты и версии до/после top-k и в Python request.
Для больших таблиц/меньших лимитов эта эвристика не гарантирует полный контекст:
требуется структурный chunking, а не безграничное расширение соседей.

Проверка EXPLAIN ANALYZE на 12 001 chunks после обновления статистики:
оба FTS-этапа используют существующий GIN, диапазоны соседей — существующий
B-tree по версии/index; planning 6.7 ms, execution 1.3 ms на тестовом наборе.
При трёх strict-источниках relaxed GIN имеет Actual Loops=0.

## До и после: retrieval отдельно от генерации

| Вопрос | Search до | Chat до | Search после / Python input | Реальный Chat после |
| --- | --- | --- | --- | --- |
| Кто входит в состав рабочей группы? | 0 | no_sources | 5: пункт 1 + заголовок + три роли | clarification либо insufficient_information/no_sources: Qwen не всегда использует известные роли |
| Какие обязанности у руководителя рабочей группы? | 1: пункт 3 | generated | 1: пункт 3 | generated, верные обязанности |
| За что отвечает секретарь рабочей группы? | 0 | no_sources | 1: пункт 4 | generated, заседания и хранение материалов |
| Кто контролирует исполнение распоряжения? | 0 | no_sources | 1: пункт 6 | no_sources: Python вернул insufficient_information из-за пустого назначения |

Последние столбцы не означают четыре полноценных генеративных ответа. Retrieval
исправлен для всех четырёх вопросов, но Qwen отдельно решает, достаточно ли фактов.
Go сохраняет текущий контракт: needs_clarification → clarification,
insufficient_information → no_sources с пустыми карточками. Вопрос 4 теперь
теряет карточку **после Python**, а не в SQL. Не добавлялись фиксированные ответы,
не подменялось воздержание модели выдуманным назначением.

Чтобы вместо уточнения/общего no_sources получить полезный частичный grounded
ответ с цитатой и указанием незаполненного поля, подготовлено
[отдельное задание Python-разработчику](tasks/python-docx-table-context.md).
Python и Qwen prompts в этой задаче не изменялись.

## Проверки

`TestIntegrationWorkingGroupRAGBoundary` использует query-independent extractive
HTTP double только для проверки передачи источников. Его текст не является
результатом тестирования Qwen. `TestIntegrationWorkingGroupQwen` отдельно
вызывает настоящий ingestion и модель, допускает безопасное уточнение/воздержание
для пустых полей и проверяет, что это не было ошибкой транспорта/fallback.

Негативы: имя контролирующего, утверждение про Иванова, фамилии участников и
секретаря, конкретный срок завершения возвращают no_sources. Модель для этих
вопросов не вызывается. Дополнительно проверяются непустые реальные цитаты при
generated, отсутствие подмены контролирующего подписантом, вымышленных ФИО/дат,
скрытые документы, неопубликованная ready-версия, неготовый документ, ACL revoke,
границы таблиц и прежние phrase/OR/exclusion-ограничения.

Это регрессия конкретного документа/модели, а не доказательство отсутствия любых
галлюцинаций на произвольном корпусе. Пустые поля нельзя восстановить embeddings.

Результат проверки: полный `go test -p 1 ./...` с тестовой PostgreSQL, проверки
поиска/границ RAG с `-race`, `go vet` и сборка проходят. Отдельный опциональный
`TestIntegrationWorkingGroupQwen` подтвердил реальный ingestion (36 chunks),
правильный контекст для всех четырёх вопросов, верные ответы по пунктам 3/4 и
безопасное воздержание для незаполненного контролирующего. Последний запуск
**не прошёл** приёмку ответа о составе: модель вернула insufficient_information,
хотя все три роли были переданы. Предыдущие запуски давали clarification.
Это оставленная явной регрессия качества Python/Qwen, а не успешный ответ или
ошибка retrieval. Тест не принимает транспортный search-fallback за успех модели.

## Минимальный hybrid, если корпус потребует больше переформулировок

Для этих retrieval-кейсов embeddings не понадобились. Дальнейшее расширение
ручных лексических семейств ограничено; при необходимости:

1. Хранить embedding каждого chunk с model/version в PostgreSQL pgvector;
   рассчитывать асинхронно после ingestion, исходные chunks остаются источником.
2. Получать, например, 20 FTS и 20 dense-кандидатов. В **каждой SQL-ветке**
   применять те же ACL/user/active-ready predicates до передачи текста в Go.
   Учитывать recall фильтрованного ANN (iterative scans/oversampling), а не брать
   глобальный top-k и затем фильтровать доступ в приложении.
3. Объединять по chunk_id через RRF, раскрывать разрешённый структурный контекст,
   применять общий top-k/бюджет и сохранять provenance всех переданных источников.
4. Настроить пороги/воздержание по положительным и негативным вопросам корпуса.
   Не считать dense-score доказательством факта; Qwen отвечает только по источникам.

Hybrid, новые зависимости, миграции или embedding-сервис здесь не внедрялись.
