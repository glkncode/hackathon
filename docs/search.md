# Search API: PostgreSQL Russian FTS

Сохраняемые диалоги поверх этого поиска описаны в [Chat API](chat.md).

Поиск возвращает сохранённые фрагменты и точные метаданные источников. Он не
генерирует ответ, не вызывает Python или LLM и не требует работающего ingestion
worker. Для поиска нужны уже сохранённые chunks активной версии со статусом ready.

## HTTP-контракт

```http
POST /api/v1/search
Content-Type: application/json
Cookie: ai_session=<session cookie>
Origin: <configured trusted origin>
X-CSRF-Token: <session CSRF token>
```

```json
{
  "query": "Как согласовать служебную записку?",
  "limit": 10
}
```

Пример формы ответа (данные иллюстративные):

```json
{
  "query": "Как согласовать служебную записку?",
  "mode": "search",
  "results": [
    {
      "chunk_id": "50863de6-a38f-4715-acf6-57e140ec663f",
      "document_id": "8d2f02ae-405d-43af-bd04-694f7bb21143",
      "document_version_id": "dc5e665c-ef5c-4304-9389-32cdc2395804",
      "document_title": "Инструкция по документообороту",
      "version_number": 2,
      "chunk_index": 3,
      "content": "Текст сохранённого пункта инструкции...",
      "page_number": 12,
      "section_number": "2.3.1",
      "section_title": "Согласование документов",
      "score": 0.42
    }
  ],
  "total": 1
}
```

`mode` всегда `search`. `score` — внутренний составной ранг, а не вероятность
достоверности: strict имеет приоритет над relaxed, внутри этапа учитываются
FTS-ранг и покрытие значимых слов. Номер страницы берётся из chunks без генерации.
Номер пункта уточняется по явному нумерованному началу самого фрагмента; явно
ошибочный заголовок возвращается как null (подробнее ниже). IDs и версия соответствуют существующей
активной ready-версии документа. Для открытия точного оригинала используйте
`GET /api/v1/documents/{document_id}/versions/{document_version_id}/download`:
endpoint повторно применяет существующие auth/ACL.

При отсутствии совпадений:

```json
{"query":"несуществующееслово","mode":"search","results":[],"total":0}
```

`total` равен **длине results после LIMIT**, а не общему количеству совпадений в
БД. Если совпало 50 разрешённых чанков и limit=10, ответ содержит total=10.
Отдельного COUNT, пагинации и сведений о запрещённых документах нет.

| Параметр | Правило |
| --- | --- |
| query | Строка UTF-8, непустая после TrimSpace, без NUL |
| Длина query | Максимум 500 Unicode-символов, включая окружающие пробелы до нормализации |
| limit | По умолчанию 10; отсутствующее/null/0 значение выбирает default; допустимы 1..30 |
| JSON | Только query и limit; неизвестные поля и лишние JSON-значения запрещены |
| Тело запроса | Максимум 4096 байт, общий JSON helper существующего API |
| Запрос в БД | Не более 5 секунд; меньший deadline/cancellation вызывающего контекста сохраняется |

В ответе query очищен от окружающих пробелов. Пунктуация и стоп-слова могут дать
пустой tsquery: это нормальный результат 200 с пустым results. Поиск лексический:
он не переформулирует вопрос и не гарантирует понимание произвольного вопроса
естественным языком. `websearch_to_tsquery` поддерживает кавычки для фразы, `OR`
для альтернатив и минус для исключения. Для таких запросов relaxed отключён,
чтобы сохранить условия пользователя; ACL действует на все варианты выражения.

## Два этапа и порог релевантности

1. **Strict:** исходный `websearch_to_tsquery('russian', query)` должен совпасть
   с content. Ранг — `1 + ts_rank_cd(weighted_vector, strict_query, 32)`.
2. **Relaxed:** выполняется, если strict дал меньше `min(limit, 3)` источников.
   `to_tsvector('russian', query)` нормализует русскую морфологию и удаляет
   стандартные стоп-слова. Из уникальных лексем исключается ограниченная общая
   рамка вопроса: «какие/какой/каков», «обязанности», «должен/должна/должны/должно»;
   «делать» исключается только при наличии «должен» и его перечисленных форм.
   Дополнительно распознаются рамки «за что отвечает …» и «… входит в состав …»;
   их глаголы не удаляются произвольно из остальных вопросов.
   Все остальные слова, включая действующее лицо, зарплату, отпуск или утечку,
   остаются значимыми. Для подтверждённых пробелов русского стеммера заданы две
   семьи: `соста/состав` и `контрол/контролир`. Покрытие считает семью один раз,
   даже если встретились оба варианта. Из нормализованных лексем строится OR-tsquery.

OR служит только индексному отбору кандидатов. Для основного совпадения **в самом content**
должны встретиться как минимум **две уникальные значимые лексемы и 80% всех
значимых лексем**. Повторы слов не увеличивают покрытие. При одной значимой
лексеме relaxed отключён: такой общий вопрос не имеет достаточного контекста.
Название документа и section_title не могут компенсировать отсутствие слов
в content. Порог проверяется до сортировки и LIMIT; нерелевантные кандидаты
не добавляются ради заполнения limit. Дубликаты strict-источников исключаются.

Для совпавшего нумерованного абзаца, оканчивающегося двоеточием, SQL дополнительно
возвращает непосредственно следующие табличные строки (признак текущего parser —
табуляция между ячейками). Только та же версия/секция, максимум 8 соседних позиций;
обычный абзац или смена секции прекращает расширение. Все проверки user/ACL,
active_version и ready повторены в SQL, а content и chunk_id остаются исходными.
Это структурный контекст доказанного совпадения, а не понижение порога для
произвольных chunks. Дополнительные строки сортируются сразу за родительским
совпадением и учитываются в общем LIMIT. Для явных phrase/OR/exclusion-запросов
расширение отключено. У больших таблиц или маленького limit контекст может быть
неполным; правильное постоянное решение — связный chunking таблиц, описанный
в [отдельном задании Python-разработчику](tasks/python-docx-table-context.md).

Весовые категории: content — A (1.0), проверенный section_title — B (0.4),
название документа — C (0.2). Нормализация `ts_rank_cd(..., 32)` даёт rank/(rank+1).
Relaxed score = `0.7 * coverage + 0.3 * normalized_rank`, поэтому любой strict
источник сортируется выше relaxed. Далее применяется прежний стабильный порядок
по document/version/chunk_index/chunk_id. Поля HTTP-ответа не меняются.

Это консервативный лексический поиск. Он не доказывает смысловую полноту ответа,
не раскрывает произвольные синонимы и не заменяет проверку grounded-ответа в RAG.

### Воспроизведение на исходном DOCX

HTTP-регрессия проверяет SHA-256 `data/demo/*создании_рабоч*.docx` и использует
golden-вывод настоящего Python parser/chunker: 36 chunks, включая строки таблицы
и унаследованные метаданные. Прежняя Go-аппроксимация по отдельным абзацам
не моделировала целостность строк таблицы и заменена этим fixture.
Optional Qwen acceptance загружает сам DOCX через настоящий Go ingestion client
в Python, сравнивает все chunks с fixture и сохраняет именно Python-ответ в БД.
До изменения оба `websearch_to_tsquery` выглядели так:

```text
организовать работу распределить задачи
→ 'организова' & 'работ' & 'распредел' & 'задач'

Какие обязанности у руководителя рабочей группы?
→ 'как' & 'обязан' & 'руководител' & 'рабоч' & 'групп'
```

Пункт 3 не содержит `как` и `обязан`, поэтому второй strict-запрос пуст.
Relaxed оставляет `групп | рабоч | руководител`: покрытие пункта 3 — 3/3.

| Запрос | До | После |
| --- | --- | --- |
| организовать работу распределить задачи | Пункт 3 | Пункт 3, strict |
| Какие обязанности у руководителя рабочей группы? | Нет источников | Пункт 3, relaxed |
| Что должен делать руководитель рабочей группы? | Нет источников | Пункт 3, relaxed |
| Какие обязанности у секретаря рабочей группы? | Нет источников | Пункт 4, relaxed |
| Какая зарплата у руководителя рабочей группы? | Нет источников | Нет источников, покрытие 3/4 < 80% |
| Как руководителю рабочей группы оформить отпуск? | Нет источников | Нет источников |
| Какие обязанности у бухгалтера рабочей группы? | Нет источников | Нет источников |

Для негативных вопросов проверяется и настоящий Chat API: `mode=no_sources`,
`sources=[]`, без изменения его реализации или контракта.

### Метаданные DOCX

Текущий ingestion распознаёт короткую нумерованную строку как заголовок.
В исходном DOCX строка «3. Руководителю Рабочей группы организовать работу…»
является распоряжением, но в section_title может попадать всё предложение.
Поисковая SQL-проекция консервативно исправляет существующие данные при чтении:

- Явное начало `3.`/`3)`/`3.1` определяет номер; обычное начало «2026 год» не определяет раздел.
- Если номер противоречит сохранённому section_number, устаревший title скрывается.
- Если title дословно дублирует весь нумерованный пункт и заканчивается знаком
  предложения (в том числе перед примечанием `[7]`) либо длиннее 120 символов,
  он скрывается как ненадёжный.
- Настоящие заголовки вроде «3.1 Общие положения» сохраняются. Новое название
  «Обязанности руководителя» не выдумывается: у пункта 3 section_title=null.

Content, IDs, исходные chunks и нумерация страниц не меняются. Ненадёжный title
исключён и из ранжирования. Это ограниченная коррекция очевидных противоречий
в выдаче поиска, а не полное исправление эвристики всех форматов ingestion.
Та же SQL-проекция используется при чтении сохранённых Chat-цитат, чтобы ответ,
идемпотентный повтор и история не возвращали старый ошибочный title. HTTP-схема
Chat, правила доступа и логика генерации не меняются.

Статусы используют существующий JSON-формат `{"error":"..."}`:

| Статус | Значение |
| --- | --- |
| 200 | Успешный поиск, включая отсутствие совпадений |
| 400 | Невалидные JSON, Content-Type, query или limit |
| 401 | Нет действующей сессии; пользователь неактивен |
| 403 | Неверные/отсутствующие Origin или CSRF |
| 500 | Ошибка БД, таймаут или другая внутренняя ошибка; детали SQL скрыты |

Чужие документы и отсутствие совпадений не различаются по структуре ответа.
Поиск доступен admin и member; роль и user_id не принимаются из тела.

## SQL и ACL

Схема и индекс миграций 00003–00005 достаточны. Новые миграции/индексы не нужны:
существующий `document_chunks_content_fts_idx` индексирует именно
`to_tsvector('russian'::regconfig, content)`. Это же выражение использовано в
предикате поиска. PostgreSQL выбирает план с учётом объёма данных и селективности;
на маленькой таблице последовательное сканирование тоже может быть оптимальным.

Оба этапа находятся в одном параметризованном SQL statement/snapshot. Strict
материализуется с LIMIT; relaxed имеет условие на число strict-результатов.
Схематически индексный отбор каждого этапа выглядит так (полный запрос — в
`internal/repository/postgres/search_repository.go`):

```sql
WITH search_query AS (
    SELECT websearch_to_tsquery('russian'::regconfig, $3) AS strict_query
    -- relaxed_query: OR из безопасно экранированных нормализованных лексем,
    -- полученных через tsvector_to_array, без конкатенации исходного SQL-ввода.
)
SELECT c.id, d.id, v.id, d.title, v.version_number, c.chunk_index,
       c.content, c.page_number, c.section_number, c.section_title,
       ts_rank_cd(to_tsvector('russian'::regconfig, c.content), q.strict_query, 32) AS score
FROM document_chunks c
JOIN document_versions v ON v.id = c.document_version_id
JOIN documents d ON d.id = v.document_id AND d.active_version_id = v.id
JOIN users u ON u.id = $1 AND u.is_active AND u.role = $2
CROSS JOIN search_query q
WHERE v.status = 'ready'
  AND (u.role = 'admin' OR EXISTS (
      SELECT 1 FROM document_access a
      WHERE a.document_id = d.id AND a.user_id = u.id
  ))
  AND to_tsvector('russian'::regconfig, c.content) @@ q.strict_query
ORDER BY score DESC, d.id ASC, v.id ASC, c.chunk_index ASC, c.id ASC
LIMIT $4;
```

Relaxed сохраняет тот же индексный предикат с `@@ q.relaxed_query` и **все те же
JOIN/ACL/active/ready/user predicates**; после отбора считает пересечение
`tsvector_to_array(content_vector)` с уникальными значимыми лексемами вопроса.
Нет `ILIKE '%...%'`, substring-поиска, сканирования всех chunks в Go или
отдельного запроса для каждого слова. Покрытие, metadata и ранг вычисляются
для кандидатов, а общие query/terms CTE вычисляются один раз.

Тест плана на 12 001 chunks после `VACUUM ANALYZE` подтвердил два `Bitmap Index
Scan` по `document_chunks_content_fts_idx`, без принудительного отключения seqscan;
пример локального запуска после коррекции DOCX retrieval: planning 6.7 ms,
execution 1.3 ms. Это результат
конкретного тестового набора, а не гарантия задержки. На маленькой таблице или
при широком запросе PostgreSQL может обоснованно выбрать другой план.

Параметры: доверенные user ID, роль, текст запроса и limit. Ввод пользователя не
конкатенируется с SQL. Фильтрация ACL, active/ready и поиск выполняются в одном
statement/snapshot до возврата данных в Go. Member должен иметь строку в
document_access; admin не требует ACL. Состояние пользователя и совпадение роли
дополнительно проверяются в БД, чтобы устаревший контекст не расширил доступ после
деактивации/смены роли. Отозванный ACL исключается из следующего SQL-запроса после
commit; уже выполняющийся запрос использует свой снимок PostgreSQL. Кэша прав или
результатов нет.

Неактивные/неизвестные версии, historical ready и ещё не опубликованные ready
не участвуют в выдаче. Изменение активного указателя сразу меняет выбор версии
для следующих поисков. Ошибка чтения БД не возвращает частичную выборку.

## Слои и будущее использование

- Domain содержит SearchQuery с нормализацией/ограничениями и SearchResult —
  проекцию цитаты с идентификаторами чанка, документа и версии. DocumentChunk
  остаётся моделью хранения; в SearchResult нет служебных timestamps/storage key.
- SearchService проверяет активного actor, ID, роль, текст и limit, затем вызывает
  потребительский интерфейс SearchStore, объявленный рядом с сервисом.
- PostgreSQL SearchRepository выполняет один ограниченный по времени запрос и
  возвращает только разрешённые источники.
- HTTP handler берёт actor из существующего auth context и использует общие JSON
  helpers, RequireAuth и OriginPolicy.CSRF.

ChatService получает тот же `*service.SearchService` через DI и вызывает
его напрямую, без HTTP:

```go
sources, err := search.Search(ctx, authenticatedUser, domain.SearchQuery{
    Query: question,
    Limit: 10,
})
```

`authenticatedUser` должен поступать из доверенной аутентификации. Передавать
модели можно только успешно полученные источники; нельзя повторно получать все
чанки в обход ACL или переиспользовать результаты другого пользователя. LLM,
контракт Chat API и Python RAG в этом изменении не меняются.

## Безопасность текста

POST не помещает запрос в URL. Go не логирует query, body или содержимое чанков.
Ответы имеют JSON Content-Type, `Cache-Control: no-store` и nosniff. Контент
возвращается как текст, без HTML-подсветки. JSON encoder экранирует HTML-символы,
но после разбора JSON исходный текст всё равно недоверенный: клиент должен
использовать безопасный текстовый вывод, без innerHTML/dangerouslySetInnerHTML.
