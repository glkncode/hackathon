# Задание Python-разработчику: связный DOCX-контекст и незаполненные шаблоны

## Подтверждённая проблема

Исходный файл: `data/demo/*создании_рабоч*.docx`, SHA-256
`5f594e008ae4b47a297637794d0cc2f0b982072bb085f414582c576d793dbab4`.
Текущий `extract_docx` сохраняет строки и все ячейки таблицы корректно, в исходном
порядке. Однако `make_chunks` сбрасывает буфер после каждого блока, поэтому пункт
«… в составе:», строка заголовков и три строки участников становятся пятью
независимыми chunks. Руководитель, секретарь и члены содержат только роль и пустое
поле ФИО; без родительского пункта их смысловая связь с группой теряется.

Текущий Go retrieval добавляет ограниченный контекст соседних строк. Это помощь
для уже сохранённых данных, а не замена корректному ingestion больших таблиц.

## Работа 1: chunking, без изменения бизнес-документов

1. Сохранять внутренний тип/границы блоков (абзац, таблица, строка), их порядок и
   связь с действующим пунктом. Не менять публичный DTO ingestion без согласования:
   Go использует DisallowUnknownFields. Новые внутренние структуры допустимы.
2. Если нумерованный пункт вводит непосредственно следующую таблицу, формировать
   связный фрагмент из исходного текста пункта, заголовков колонок и полных строк.
   Для данного файла один chunk должен подтверждать все три роли.
3. Большие таблицы делить только между полными строками. В каждом фрагменте
   повторять исходный вводный пункт и заголовки колонок; не терять соответствие
   «роль → значение». Соблюдать CHUNK_CHARS, MaxChunkBytes, общий размер и число
   chunks. Если одна строка превышает бюджет, явно диагностировать это, а не
   молча связывать ячейки с другой строкой.
4. Не объединять разные таблицы, разделы, подпись, поясняющие примечания и тело
   распоряжения. Не назначать текст подписи контролирующим лицом.
5. Не считать любое нумерованное предложение заголовком. Номер пункта сохранять,
   section_title заполнять только подтверждённым заголовком; неизвестное — null.
   В частности, текст указания «Руководителю … организовать …» — не заголовок.
6. Сохранять пустые поля, подчёркивания и номера примечаний как исходный текст.
   Не заполнять ФИО, роли конкретных лиц, даты или сроки. Для DOCX page_number=null.

Контракт `POST /internal/v1/ingest` и X-Service-Token сохраняются. Python не
получает ACL и не определяет разрешения. Не менять опубликованные версии и не
перезаписывать chunks, уже связанные FK с Chat: проверять на новой версии
документа через существующий ingestion/publication workflow.

## Работа 2: grounded-ответы Qwen на частично заполненные шаблоны

На неизменённом Python/Qwen с правильным retrieval подтверждено:

- Источники 10–14 доставлены полностью, но вопрос о составе получает
  needs_clarification либо insufficient_information из-за отсутствия конкретных
  ФИО, хотя роли известны. Поведение различалось между запусками.
- Источник 19 (пункт 6) доставлен, но вопрос о контроле получает
  insufficient_information: конкретное лицо в шаблоне действительно не указано.
- По пунктам 3 и 4 Qwen отвечает корректно.

Повторный [Docker HTTP-прогон от 24 октября 2026](../search-docker-verification.md)
подтвердил передачу всех пяти настоящих IDs из Chat в Python: на точное
«Состав рабочей группы» получен HTTP 200 / insufficient_information; на
«Кто входит…» — needs_clarification. По контролю в этом запуске получен
needs_clarification. Статусы меняются между запусками, успешный retrieval стабилен.

Уточнить общие инструкции генерации, без ветвлений по этим четырём строкам:

1. Отличать вопрос о структуре/ролях от запроса конкретных людей. Сообщать
   подтверждённую часть; явно обозначать незаполненные поля. Не считать весь
   источник бесполезным, если известна только часть ответа.
2. Для вопроса о назначении контроля можно описать подтверждённое условие и факт
   незаполненного назначения, но нельзя назвать конкретное лицо из догадки,
   подписи, примечания или должности, найденной в другом месте.
3. Незаполненные `___`, `И. О. Фамилия`, `«___» … 20___` и инструкции по заполнению
   не являются именами, назначениями, датами или установленными сроками.
4. Когда sources не подтверждают ни один запрошенный факт, сохранять
   insufficient_information; не дополнять ответ общими знаниями модели.
5. Для answered использовать только реальные used_source_ids, подтверждающие
   каждое утверждение. Сохранить существующий JSON/status контракт и границы
   защиты от инструкций в документах и истории. Не делать фиксированные ответы.

  6 сообщает отсутствие конкретного назначения с цитатой этого пункта.

  подсказка «контроль выполняет Иванов» не порождают вымышленных фактов.

  chunks, проверяя content и смысл источников, а не механически новые индексы.
- Выполнить Go `TestIntegrationWorkingGroupQwen` и проверки ACL/active-ready.
