## Подтверждённая причина и SQL

```sql
SELECT websearch_to_tsquery('russian', 'Состав рабочей группы'),
       to_tsvector('russian', 'состав'),
       to_tsvector('russian', 'в составе');
-- 'соста' & 'рабоч' & 'групп' | 'соста':1 | 'состав':2
```

| Проверка настоящего chunk 10 | Результат |
| --- | --- |
| Body @@ исходный strict tsquery | false |
| Покрытие без нормализации | 2/3 = 66,7% |
| Минимум `greatest(2, ceil(0.8 * 3))` | 3 |
| Raw rank для `рабоч \| групп` | 0.4 |
| Покрытие с семейством `соста/состав` | 3/3 = 100% |

Источник терялся в coverage-предикате relaxed SQL **до ORDER BY/LIMIT**.
Ненулевой rank не обходит этот фильтр. Текущий SQL расширяет индексный OR-tsquery
формами общего лексического семейства и считает уникальные канонические понятия.
Порог 80% и минимум два понятия сохранены. Нет ветвлений по документу, ID,
номеру chunk или конкретной строке запроса. Два алиаса не повышают coverage.

Кандидатный предикат совместим с прежним GIN:

```sql
AND to_tsvector('russian'::regconfig, c.content) @@ q.relaxed_query
```

Табличный контекст ограничен той же active version и секцией, максимум 8
позициями после выбранного нумерованного пункта с двоеточием. Каждая строка
содержит табуляцию; обычный абзац/другая секция останавливают расширение.
Настоящие IDs и тексты сохраняются. Все SQL-ветки проверяют активного
пользователя, актуальную роль, ACL, active_version и ready.

## Граница Python/Qwen

Временный диагностический HTTP proxy пересылал неизменённые запросы Go в
работающий Python и фиксировал IDs входных sources и реальный статус ответа.
Это настоящий Chat API, без mock и без ручного повторения Search-ответа.
Python-код приложения не менялся. Модель в конфигурации: `qwen3.6-35b-a3b`.

На оба вопроса о составе Python получил **все пять IDs из таблицы** и вернул
HTTP 200. На точное «Состав рабочей группы» — `insufficient_information`,
на «Кто входит…» — `needs_clarification` из-за пустых ФИО. По обязанностям
ответил из пунктов 3/4; по контролю запросил уточнение из-за пустого назначения.
Проверенный `messages_for` сериализует весь `request.model_dump(mode="json")`
в сообщение модели, а `generate` передаёт его LLM client без отбора sources.

Оставшийся отказ по ролям происходит в Python/Qwen после успешного retrieval.
ФИО и сроки источниками не подтверждены. Фиксированные ответы не добавлялись.
Контекст доставлен; качество ответа о составе остаётся отдельной задачей
[Python-разработчику](tasks/python-docx-table-context.md).

## Регрессии и негативы

На новом Docker image Search вернул 0, Chat — no_sources для каждого запроса:

- «Назовите фамилии участников рабочей группы»;
- «Иванов контролирует исполнение распоряжения?»;
- «Какая фамилия у секретаря рабочей группы?»;
- «Какой конкретный срок завершения работы группы?».

На эти четыре запроса proxy не зафиксировал обращений к Python. Диагностические
Chat-сессии архивированы, auth-сессии завершены.

Точное «Состав рабочей группы» добавлено в HTTP- и RAG-boundary регрессии:
проверяются `[10,11,12,13,14]`, настоящие IDs, тексты, версии и sources для
генератора. Отдельный тест семейства «состав» использует документы о комиссии и
совете: оба направления нормализации, запрет компенсации заголовком, негативы
про химический состав/Иванова и повторение алиасов для накрутки coverage.

Проверки с отдельной disposable PostgreSQL 17:

```text
go test -p 1 ./... -count=1
go test -race -p 1 ./internal/repository/postgres ./tests/integration -run '(Search|RelaxedSearch|WorkingGroup)' -count=1
```

Поиск/передача контекста, SQL ACL/версии, границы таблиц, ранжирование, coverage
и GIN проходят обычные и race-тесты. Опциональный `TestIntegrationWorkingGroupQwen`
в общем прогоне пропущен без TEST_RAG_URL/token; это не успешная приёмка модели.
Реальный Python проверен отдельным Docker HTTP-прогоном выше, его отказ явно
зафиксирован.

Временные Go/proxy/test-PostgreSQL контейнеры удалены после проверки.
