## Причины и изменения

### Resolver и история

При выключенном Resolver история этой сессии читается после поиска и передаётся
генератору. E5, FTS и Evidence Gate получают текущий вопрос без истории.
Поэтому «А во сколько его возвращать?» может иметь десять кандидатов, но
получить пустой вердикт Gate: модель генерации даже не вызывается.

С включённым существующим флагом до поиска читается ограниченная история
владельца с текущими ACL. Сохраняются прежние границы темы, provenance,
ограничение числа сообщений, пропуск скрытых ответов и защита после отзыва
доступа. Resolver не получает документы и не отвечает пользователю фактами.

Изменения в `ai-service/app/rag/resolver.py` и `internal/aiclient/resolve.go`:

1. В промпте явно разделены неизвестный факт и неизвестный предмет. Цена, срок,
   правило или документ могут отсутствовать; это не основание спрашивать
   пользователя о предмете, уже определённом историей. Новое условие заменяет
   старое, самостоятельная новая тема не наследует старый предмет.
2. Сервер сам восстанавливает полную исходную строку, если модель не заполнила
   `queries`. Исходный вопрос остаётся отдельной поисковой веткой. Сохраняются
   проверки дословных якорей, бюджета, JSON, индексов и состояний.
3. При непустой истории для уточнения нужны ровно две разные дословные
   альтернативы из неё. Python и Go проверяют их; один вопрос о выборе строит
   сервер. Уточнение без этих оснований отклоняется с
   `resolver_clarification_rejected`, работает прежний Semantic Search.
4. Удалён второй Qwen-вызов, который раньше проверял предложенное уточнение,
   но сам мог подтвердить ненужный вопрос. Теперь одна попытка на запрос,
   без автоматического повторения. Существующие таймаут 8 секунд, feature flag
   и метрики сохранены.

Это ограничивает неподтверждённые уточнения, но не доказывает семантическую
правильность якоря. Модель всё ещё может выбрать старое условие или целое
предыдущее предложение вместо названия предмета. При пустой истории проверка
двух альтернатив неприменима — здесь обнаружена оставшаяся ошибка.

Существующая предварительность уточнения сохранена: исходный поиск выполняется
и после `needs_clarification`; разрешённые источники могут позволить генерацию.
Пустой поиск сам по себе не создаёт `needs_clarification`, но может оставить
ошибочно предложенное моделью уточнение. Это не устранено полностью.

### Отказы и техническая недоступность

Реальная ранняя ветка находится в `internal/service/chat.go`: после успешного
поиска вызывается `domain.SearchReply(len(sources)>0)`, а Python Generate
вызывается только при непустых источниках. Изменён общий текст в
`internal/domain/chat_message.go`, используемый также для
`insufficient_information` генератора:

> В доступных мне документах не нашлось подтверждённой информации по вашему
> вопросу. Если это поможет, укажите название документа или обстоятельства ситуации.

Это сообщение не раскрывает наличие закрытых документов и не утверждает, что
пользователь обязан уточнить уже понятный вопрос. Настоящее уточнение остаётся
отдельным режимом `clarification`.

В `internal/service/semantic_search.go` сохранён FTS fallback. Если он пуст
после технической ошибки embedding, векторного поиска или Gate, возвращается
новый `domain.ErrSearchUnavailable`. Обработчики поиска и чата возвращают 503
с предложением повторить запрос позднее. Ложный ответ `no_sources` не сохраняется.
Пустой допустимый вердикт Gate по-прежнему означает отказ, без обхода Gate.
Настоящий пустой набор кандидатов по-прежнему допускает обычный пустой FTS.

В логах причины различаются:

| Причина | Признак |
| --- | --- |
| Нет кандидатов | `retrieval verdict: no_candidates/no_visible_candidates` |
| Gate не нашёл подтверждений | `evidence_rejected`, число кандидатов ненулевое |
| Техническая ошибка Gate | `evidence gate completed: success=false`, отдельный `error_code` |
| Генератору не хватает сведений | `chat generation completed: insufficient_information` |
| Ошибка генерации/контракта | `chat RAG fallback`, причина; прежний режим поиска |
| Ошибка Resolver | `chat context resolver completed: fallback/timeout`, причина и число вызовов |

### Отклонённый кандидат стиля

Эксперимент добавлял инструкции понятного языка к неизменному системному промпту.
Измеримого улучшения не обнаружено, возникла регрессия статуса. При уборке
ветка, флаг и отдельный тест удалены; исходный промпт Generator сохранён.
История эксперимента находится во внешнем архиве из [отчёта](repository-cleanup-report.md).

## Как проводилась проверка

Перед редактированием заморожен исходный Go/Python в
`.local-integration/rag-improvement/baseline`, включая Go overlay и хеши.
Сначала использовались отдельные development-документы, затем зафиксирован
`experiments/context-dialogue/corpus-v2-holdout.json`: пять новых разрешённых
документов, один закрытый, три отдельные сессии, 22 последовательных вопроса.
Содержание документов не добавлялось в production-код.

Варианты: исходный RAG с выключенным Resolver; доработки с включённым Resolver;
те же доработки с дополнительным абзацем стиля. Последний вариант проверяет
добавку стиля к контекстному пути, отдельный вариант «стиль без Resolver» не измерен.
Это сравнение сборок, а не доказательство вклада каждой строки кода.

Использованы реальные Qwen, E5-small, pgvector, SQL-фильтрация и Evidence Gate.
Изолированные контейнеры и временная БД не затрагивали основной проектный
корпус. Все варианты прошли одни и те же вопросы один раз; неудачные ответы
не заменялись повторными вызовами. После чтения holdout production-код не менялся.
Менялась только запись результатов контрольной проверки, прежде терявшая
артефакт при assertion failure. Утечки цитат и чужой сессии остаются жёсткими
ошибками; несовпадение качественного статуса записывается отдельно.

Все 66 фактических ответов просмотрены вместе с источниками. Ручная разметка
агента находится в `review.json`; это не независимая человеческая экспертиза.
Статус `generated` сам по себе не считается успехом. Общий балл требует
правильного статуса, подтверждённых утверждений, полноты, уместного уточнения
и правильного отказа. У вопроса с несколькими условными ответами необязательный
выбор условия считается ошибкой уточнения.

*В baseline один технический сбой был ошибочно замаскирован `no_sources`.
Формальная проверка всех выданных цитат прошла: разрешённый документ, точный
текст фрагмента, индекс и версия 1. Принадлежность source IDs проверяется
существующими валидаторами. Проверка смыслового подтверждения — ручная.
В сгенерированных ответах новых ложных утверждений не обнаружено; это не
означает 100% правильности системы: отказы, неполнота и лишние уточнения
учитываются отдельно. Неполученный ответ не засчитывается как сохранение условий.

Конкретные улучшения:

- «А во сколько его возвращать?» после зажима: baseline имел десять кандидатов,
  но Gate отказал; исправленный путь назвал 16:45 в день выдачи и 08:35 следующего
  дня с правильными условиями и источником.
- После перехода к тепловизору «А до какого времени его вернуть?»:
  исправленный путь назвал 19:15/10:25, без переноса сроков зажима.
- «А какие нужны документы?» в новой пустой сессии: вместо пустого отказа задан
  конкретный вопрос о процедуре; последующий ответ пользователя позволил поиск.
- Многошаговое архивирование сохранило все пять действий и два подтверждающих
  фрагмента. Выходное согласование не отменило проверку перечня. Пустые поля
  шаблона не превратились в выдуманные лицо и дату.

Реальные причины неудач и оставшиеся ошибки:

1. Baseline: шесть `evidence_rejected`, включая два ошибочных отказа на
   местоименных вопросах и отказ вместо уточнения без предмета. Ещё один
   `evidence_invalid_response` → пустой FTS → ложный `no_sources` на вопросе
   об электронной/бумажной подписи. Отказ генератора здесь не был причиной.
2. Исправленный Resolver: три `evidence_rejected`, все соответствовали
   отрицательным вопросам или предварительному уточнению. На вопрос о штрафе
   генератор отдельно вернул `insufficient_information`. Один ошибочный план
   уточнения на ответ пользователя о передаче образцов отклонён валидатором;
   Semantic Search fallback дал правильный ответ.
3. Во всех трёх вариантах после сравнения **дневных** сроков «А когда его
   возвращать?» генератор верно спрашивает о предмете, но дополнительно требует
   уточнить смену. Это не один необходимый вопрос; условие уже известно.
4. В варианте стиля правильный источник о сроках тепловизора был передан
   генератору, но тот потребовал выбрать тип бронирования вместо ответа с двумя
   условиями. На сканировании произошёл `evidence_invalid_response`; новая
   обработка вернула `search_unavailable`, без ложного заявления об отсутствии
   сведений. Разные одиночные прогоны не доказывают, что сбой Gate вызван стилем.
5. Дополнительный контроль без прав на документы: baseline вернул `no_sources`.
   После 22 вопросов context тест завершился ошибкой `no-candidates handling
   <nil>` до записи контрольного ответа. Его фактический режим и список цитат
   не сохранены: результат нельзя объявить успешным или приписать ему конкретный
   ответ. Сбой записан в `v2-final-context/control-failure.json`, не перезапускался.
   У style контроль записан полностью: ноль кандидатов и цитат, чужая сессия
   недоступна, но Resolver спросил, является ли явно названный телескоп
   инструментом, ПО или организацией. Это ненужное уточнение с придуманными
   трактовками. Контроль не входит в 22 вопроса таблицы и является отдельным
   основанием оставить флаги выключенными.

Развитие кандидатов не скрыто: первый development дал 17/20, 18/20 и 20/20;
следующее сокращение промпта отклонено после ложного уточнения суммы страховки
и отказов на понятных продолжениях. Промежуточный `v2-contract-dev` сохранил
14 ответов до технического сбоя поиска. Диагностические development-replay
показали неправильную вложенность JSON и выбор старого срока как предмета.
Эти прогоны не подменяют финальную оценку.

Высокий p95 парной добавки включает переход от быстрого пустого отказа к
содержательному ответу; это не только стоимость Resolver. Дополнительный
Qwen-вызов по-прежнему стоит около 1,3 секунды. Удаление второго вызова
ограничило число попыток, но не устранило эту задержку. Контрольные вопросы
считаются отдельно: в записанном runtime style 23 запроса и 23 Qwen-вызова,
один отказ валидации и ноль таймаутов. Runtime context не записался из-за
контрольной ошибки; таблица использует сохранённые события всех 22 вопросов Go.

Выборка мала: 11 разрешённых фрагментов, top-10 покрывает почти весь корпус.
Порядок вариантов последовательный, по одному прогону, внешняя Qwen меняется
даже при temperature=0. p95 здесь описывает 22 измерения, а не нагрузочный SLA.
Нельзя переносить результат на произвольный большой корпус или приписывать
улучшение сканирования только Resolver: baseline в этом месте имел сбой Gate.

## Безопасность, схема и тесты

ACL, active-ready версии, повторная фильтрация видимости, проверка source IDs,
provenance истории, повтор запросов с тем же ключом и CSRF не отключались.
Изменений DOCX Generator, React Wizard, пользовательских документов и миграций
в рамках этой доработки нет. Уже имевшиеся изменения рабочего каталога сохранены.

Основная БД проверена только чтением до и после работы: последняя применённая
миграция **11**, столбца `chat_messages.starts_new_topic` нет. Существующая
миграция 00012 в checkout не применена. Новый Go-код использует этот столбец
даже при выключенном Resolver: такой образ требует схемы 12. Существующая
startup-проверка миграций не ослаблена. Новый основной образ не собирался и не
запускался; автоматическое применение миграции не инициировалось. Для тестов
миграции применялись только в отдельной временной БД.

Проверки: Python — 193 passed, 6 существующих пропусков, зависящих от embedding
окружения; реальная E5 работала в оценке. Go — полный набор с изолированной
PostgreSQL, отдельные тесты клиента, сервиса и HTTP; `go vet ./...` и
`git diff --check`. Успех обычных тестов не отменяет описанных ошибок модельной
оценки. Контейнеры оценки удаляются после выполнения; `down -v`, commit, push
и deploy не выполнялись.
