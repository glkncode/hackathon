# Query Understanding: диагностика и проверка Docker/Qwen

Дата: 24 октября 2026. Исходный Go commit: `6f2c6a3`.
Commit, push и deploy в этой задаче не выполнялись.

## Воспроизведение до изменений

Проверены прямые Search и Chat HTTP API текущего Docker, с настоящей
cookie/CSRF-аутентификацией и `limit=8`. Тестовый документ содержит 36 chunks:
document_id=`9a7d2e68-739f-4cf9-a935-c952e32db73b`,
active ready version=`51c3d732-b52c-44b5-a5a2-5c6fce3f7667` (версия 1).
Бизнес-документ и его chunks не изменялись.

| Запрос | strict tsquery | После удаления рамки |
| --- | --- | --- |
| секретарь | секретар | секретар |
| руководитель | руководител | руководител |
| Какие обязанности у руководителя? | как & обязан & руководител | руководител |
| За что отвечает секретарь? | отвеча & секретар | секретар |

Strict не находит естественный вопрос из-за отсутствующих слов рамки.
В relaxed после их исключения остаётся одна значимая лексема, а SQL требует
`cardinality(q.lexemes) >= 2`. Источник теряется здесь, до ранжирования/top-k;
Python для пустого поиска не вызывается. Короткие запросы обходят эту проблему
через strict FTS и действительно приводят к generated с правильным пунктом.

## Изменения

Добавлен отдельный детерминированный `internal/queryunderstanding`: исходный
вопрос и один focused-вариант с сохранением полного предмета/условий вопроса.
Общие рамки обязанностей/задач/функций не зависят от названия роли или документа.
Например, «Какие обязанности у руководителя?» → «руководителя»;
«За что отвечает секретарь при утечке данных?» → «секретарь при утечке данных».
Последний запрос остаётся неподтверждённым, тема утечки не отбрасывается.

Каждый вариант проходит прежний SQL с ACL, текущей ролью/активностью пользователя,
active_version, ready и прежним GIN. Оба запроса используют общий снимок
read-only REPEATABLE READ; суммарный бюджет 5 секунд. Кандидатов на вариант —
`max(limit,10)`, максимум 30. При ошибке нет частичного ответа.

Кандидаты объединяются через RRF (`sum(1/(60+rank))`) с дедупликацией по настоящим
chunk IDs и стабильным top-k. Для вопросов об обязанностях пустые табличные
значения «роль → ___» исключаются: сама роль не подтверждает обязанность.
Таблицы с заполненным текстом остаются источниками. Буквальные короткие запросы
не меняются. Content, IDs, ссылки, исходный вопрос в Chat и API-схемы сохранены.

Глобальный порог relaxed 80%/минимум два понятия не понижен. Focused-вариант
использует тот же strict FTS, что уже успешно обслуживал короткий запрос.
Условия/фамилии не удаляются ради совпадения. Кавычки, операторы, отрицания и
нераспознанные намерения сохраняют исходную семантику поиска.

Вызовы LLM в поиске не добавлены: доступный Python API `/internal/v1/rag/generate`
имеет контракт генерации по готовым источникам, отдельного rewrite API нет.
Использовать его для переписывания с фиктивными источниками было бы неверно.
Без LLM работает детерминированный план и PostgreSQL. Qwen используется только
на прежнем этапе ответа, с проверкой used_source_ids против переданных sources.

ответы модели, не extractive test double. По руководителю ответ содержит
организацию работы, распределение задач и соблюдение срока; по секретарю —
оформление результатов заседаний и хранение рабочих материалов. В ответе о
составе перечислены роли и явно отмечены незаполненные ФИО.

## Негативы

Каждый запрос до и после возвращает Search `[]`, Chat `no_sources`, без цитат:

- Какая зарплата у руководителя?
- За что отвечает секретарь при утечке данных?
- Какие обязанности у бухгалтера?
- Какие обязанности у руководителя по оплате труда?
- Какие обязанности у секретаря Иванова?
- Назовите фамилии участников рабочей группы.
- Какой конкретный срок завершения работы группы?

Ложные положительные результаты: **0/7 → 0/7**. Для этих семи запросов новый
Go не вызывал Python; proxy зафиксировал только 10 положительных обращений.
Система не восстанавливает отсутствующие факты из догадок.

## Время поиска

Сравнивались два временных Go-контейнера с одной PostgreSQL и одинаковыми
настройками, прямой HTTP без разницы nginx/direct маршрутов. Старый binary
SHA-256 совпадает с работающим `hackathon-api-1`:
`90ba0b62ffc3cd5cee9483c6e8fee56b1609251813395e93635cf33156eabf79`.
Новый: `c1db5b1a78b4639bc522501ece4abef7dc4916af5980cc8479229018d02de5a1`.

После двух прогревочных повторов выполнено по 30 запросов каждой из 17
формулировок на каждый image — 1020 измерений, чередуя порядок old/new.
Измерялся полный POST /search (HTTP, auth, SQL, JSON), без вызова модели.
В это время Go-тесты уже завершились, БД содержит 36 chunks.

| Группа | p50 до, мс | p50 после, мс | p95 до, мс | p95 после, мс |
| --- | ---: | ---: | ---: | ---: |
| Все 17 запросов | 2.853 | 4.078 | 3.845 | 5.283 |
| Семь естественных вопросов об обязанностях | 2.779 | 4.508 | 3.430 | 5.623 |
| Два коротких запроса | 3.193 | 3.390 | 4.131 | 4.556 |

Дополнительная медианная задержка для естественных вопросов: **1.729 мс**.
У коротких запросов путь выполнения не менялся; небольшая разница измерений
не доказывает регрессию. Числа относятся к этому локальному корпусу/прогреву,
а не являются SLA или оценкой нагрузки большого корпуса.

Семь новых успешных Chat-ответов занимали 2.25–2.38 с (медиана 2.322 с).
До изменения Chat быстро возвращал no_sources и не вызывал модель; это не
сопоставимая генерация. Query Understanding не добавляет отдельный LLM round trip.

## Проверки и окружение

Пересобран только Go image: `hackathon-go:query-understanding-verify`.
Image config: `sha256:89f86a9fbb60d77df8ce9c0eea6f368e95e11242ffb27bc1a6c4fdf4fd42f42f`.
Новый Go проверен через `127.0.0.1:18081`, старый для latency — через
`127.0.0.1:18082`. Временные контейнеры использовали текущую БД, с отключёнными
ingestion, migrations и bootstrap. Эта проверка не заменяла и не перезапускала
рабочие контейнеры.
Изменения Python, уже находившиеся в workspace до задачи, не редактировались;
оба Go image проверены с одним работающим Python/Qwen.

На отдельной disposable PostgreSQL 17 выполнены:

```text
go test -p 1 ./... -count=1
go test -race -p 1 ./internal/queryunderstanding ./internal/service ./internal/repository/postgres ./tests/integration -run '(Search|RelaxedSearch|WorkingGroup|Understand)' -count=1
go vet ./...
git diff --check
```

Проверяются распознавание рамок и сохранение условий/имён/чисел, операторы,
отрицания, неизвестный intent, ограниченный план, cancellation/ошибки без
частичных источников, RRF/дедупликация, limit=1, пустые/заполненные таблицы,
обычные роли инженера/диспетчера, SQL ACL/revoke, active-ready версии, GIN,
точные IDs, текст и metadata в Search/Chat/Python request. Тесты проходят.
Опциональная Go-приёмка Qwen без TEST_RAG_URL/token пропускается; реальные
Docker HTTP-запросы выше отдельно проверили модель, этот skip не засчитан
как успешный вызов Qwen.

Все диагностические Chat-сессии архивированы, auth-сессии завершены.
Временные Go/proxy/test-PostgreSQL контейнеры удалены после проверки.
Python ingestion, React и бизнес-документы не менялись.
